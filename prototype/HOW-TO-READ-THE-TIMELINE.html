Unravis · Investigation Timeline wireframe

A slowdown shows up. How do you get to the answer?

Six moves, in order. Each one answers one question and hands you to the next. Walk them with the demo case Payroll.Run slowdown, 20 Oct.

1 When?→2 How big?→3 Which layer?→4 Which suspect?→5 Which call?→6 Prove it

The whole idea in one picture

Mantra: compare to before → find which layer moved first → read the suspect it points to → run the one cheap check. The page does the sorting. You do the judging.

1

Set the two windows

Question: when was it bad, and compared with what?

WhereTop of the page: Investigation window and Compare it with boxes. Check the UTC label.
Look forProblem box = when users complained. Comparison box = an equal stretch just before. The demo uses 09:00–11:30 against 06:30–09:00.
It meansEvery “times the comparison period” on the page is problem ÷ comparison. Wrong windows, wrong answers.

Demo: both windows are 2 h 30 min, so counts compare like for like. The default Last hour would show different numbers (about 1,779 requests, 389 ms), because it misses the incident.

The comparison period is only a yardstick. It may not have been healthy. If it was also slow, the ratios shrink.

3

Find which layer moved first

Question: where did it start?

WhereThree lanes under the tiles: API audit, Database, Web server (IIS). They share one time axis.
Look forThe moment each lane’s line or bars jump away from the dashed comparison line. Which lane jumps earliest?
It meansTrouble travels up the stack: database → app → web. The earliest mover sits closest to the cause.

Demo: database lane lifts first (09:11), API follows (09:14), web server later. Order: DB → API → web. The database is the lead suspect.

Do it yourself, by hand

The recipe, with the arithmetic

  1. Pick two equal windows. Problem 09:00–11:30, comparison 06:30–09:00.
  2. Ratio = problem ÷ comparison. 522 ÷ 220 ≈ 2.4×. Red from 1.5×.
  3. Share = count ÷ total. 185 ÷ 4,216 = 4.4% errors. 2,005 ÷ 5,059 = 40% slow DB calls.
  4. Order the layers by first jump. Earliest line leaving its dashed baseline wins: database 09:11, API 09:14.
  5. Match the suspect. Take the red card whose tier is the earliest, and read its table.
  6. Pick the operation by change, not speed. Payroll.Run 4.9×.
  7. Run the one cheap check. Head blocker in the blocking report.

Where you land

The conclusion the page reaches

Production only. The orders database slowed first (09:11, about 25×, 40% of calls over 1 s) with 11 blocked-process reports against none before. The API followed at 09:14 and the web server after. The hurt operation is Payroll.Run (4.9×). Best-fit suspect: D1 blocking chain. Next move: find the head blocker. It is a lead, not a verdict.

Keep these honest
  • Colours are prototype defaults (1.5×, 2% errors, 25% slow). They are not yet backed by real incident data.
  • Earliest-to-move is a strong hint, not proof. Bars are 5 minutes wide and clocks can differ.
  • The numbers are demo data for the wireframe. The real product will fetch each from a named source.
  • The wireframe shows 26 suspects. The real product plans 44.
