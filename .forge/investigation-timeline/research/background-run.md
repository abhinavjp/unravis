# Background run: no console window while Unravis is up (research, read-only)

Owner ask: no console/terminal while Unravis is up; it runs in the background; a shortcut is added if missing; the installer does it. Target Windows 11, Go, no cgo. Items marked (unverified) were not proven here.

## 1. What ships and how it starts today (real code)
- Four programs, all CONSOLE subsystem. No `-H=windowsgui` anywhere in the repo's own build (grep found it only in Go toolchain tests). `build.ps1` builds `unravis.exe` (cmd/audit-explorer), `unravis-keeper.exe`, `unravis-blackbox.exe`, then `unravis-setup.exe` (embeds the first three plus a SHA-256 manifest under cmd/unravis-setup/payload); ldflags only stamp version, CGO off. `.syso` icons exist for audit-explorer and unravis-setup (made by `tools/icon/main.go`, icons only, no manifest or subsystem change). Dev scripts: `Start Live.cmd` (console wrapper, pauses on error), `run.ps1`.
- `unravis.exe` (cmd/audit-explorer/main.go): flags `--demo --port --no-browser --mcp --mcp-allow-identifiers --allow-broad-scans --docs-examined-budget --version`. Default `--port 0` = a random free loopback port each run (`listenLoopback`, tcp4 127.0.0.1). No single-instance guard: a second run just gets another port. Opens the browser with `rundll32.exe url.dll,FileProtocolHandler <url>/launch?c=<code>` (main.go ~265); the code is single-use (2 min browser / 10 min manual life, `internal/server/launch.go`) and the session token travels in the URL fragment (decision A19: "no new link or token; the existing one-time launch link stays"). Writes `session.json` (port, token, pid, owner-only) under `%APPDATA%\APIAuditExplorer` (`internal/mcp/sessionfile.go`), removed on clean shutdown only if the token matches.
- Stop today: Ctrl+C or closing the console only (`signal.NotifyContext(os.Interrupt, SIGTERM)`, 4 s drain, removes session file). No quit endpoint, no pid-based stop. The installer's close-app step says "Unravis has no way to be asked to close from outside" and terminates it after consent (`internal/setup/plan.go` closeApp), which skips clean shutdown and can leave a stale session.json.
- Output people may rely on: `log.SetOutput(io.MultiWriter(os.Stderr, logFile.Writer()))` (main.go ~169; support log dir `applog.DefaultDir`); startup lines print version and "listening at http://127.0.0.1:PORT", and when the browser was not opened (`--no-browser` or start failure) the one-time launch link; fatal startup errors go through `log.Fatal` to stderr only. README line 7 tells users to keep the terminal open.
- `unravis.exe --mcp` is a stdio MCP server spawned by AI clients (MCP.md); it finds the running dashboard through session.json. `--version` is run by the installer verify step (`plan.go` verify, `os_windows.go` runVersion with `HideWindow: true`). Both depend on stdio of unravis.exe.
- `unravis-keeper.exe`: Windows SERVICE `NT SERVICE\UnravisKeeper` (`plan.go:46`), machine scope; holds sealed SQL/Mongo passwords and Blackbox read keys, answers over a local named pipe, never returns a secret; Event Log; `console` subcommand for developers only. Windowless by design.
- `unravis-blackbox.exe`: CLI plus Windows SERVICE (auto start, `os_windows.go` ~336; `internal/blackbox/service_windows.go`); Event Log; foreground verbs print to console. Windowless by design. Neither service needs UI, so session 0 is fine for them.
- `unravis-setup.exe`: console subsystem too (a double-click shows a console beside the setup page). Setup page = loopback HTTP + Edge/Chrome `--app` window with a private profile (`internal/setup/window_windows.go`, fallback ShellExecute). `StartProgram` launches unravis.exe plainly (visible console). Single-instance precedent: `Global\UnravisSetupRun` mutex (`os_windows.go` setupLock).
- So a console appears when: the user starts unravis.exe from the Start menu shortcut, at every sign-in via the Startup shortcut, and when setup's "open when done" runs it.

## 2. What the installer creates now
- Start menu `Unravis.lnk` -> `unravis.exe`: all-users Programs (machine scope) or per-user Programs (user scope) (`internal/setup/layout.go` StartMenuLink; step "shortcuts" in `plan.go` ~132 and ~625-645).
- Startup-folder `Unravis.lnk` (same target) only if option `StartAtSignIn` (default ON in the window per `buildout/plan/installer-and-releases.md`; `options.go`, `layout.go` StartupLink). No Run key, no scheduled task.
- No Desktop shortcut and no Desktop path in `Layout` (only Programs and Startup); `CheckUserDirs` whitelists exact suffixes, so a Desktop path must be added there.
- `.lnk` writer is hand-made MS-SHLLINK bytes, no COM (`internal/setup/lnk.go`): show-command hard-coded SW_SHOWNORMAL, no AUMID/property store. Good for dependency policy; adding fields is small.
- Add/Remove Programs entry under HKLM or HKCU `...\Uninstall\Unravis` with UninstallString, QuietUninstallString, ModifyPath `--repair`, DisplayIcon (`plan.go` arp ~647-672). Uninstall removes shortcuts (`uninstall.go` removeShortcuts ~148). `--repair` re-places shortcuts.
- Keeper service (machine scope) and Blackbox service (when chosen) are registered by setup; the dashboard itself is NOT a service.
- Net: "shortcut if missing" is half there (Start menu yes, Desktop no); the console problem comes from the target being a console exe.

## 3. Windows facts (Microsoft Learn pages and the Go toolchain source in `.dev/toolchains/go/src`)
a. `-ldflags -H=windowsgui` produces a GUI-subsystem exe (cmd/link/doc.go): no console is created and stdio handles are only what the parent passes. With none, `os.NewFile` returns nil for an invalid handle (os/file_windows.go ~131), so `os.Stderr` is a nil *File and writes return an error, no panic. REAL BREAKAGE here: `io.MultiWriter(os.Stderr, logfile)` stops at the first writer error, so the support log would get nothing; `log.Fatal` becomes a silent exit; the printed launch link and startup errors vanish; `--version`/`--help` print nothing in a terminal unless `AttachConsole(ATTACH_PARENT_PROCESS)` is called first. A parent that passes pipes (installer verify, MCP client spawn) still gives the child valid handles in normal CreateProcess behaviour; for Go specifically this needs a test (unverified).
b. Hiding a child console: `CREATE_NO_WINDOW` (0x08000000) runs a console app without a console window; it is ignored with CREATE_NEW_CONSOLE or DETACHED_PROCESS and for non-console apps (MS Process Creation Flags). Go: `SysProcAttr{CreationFlags: ...}`. `HideWindow: true` only sets SW_HIDE in STARTUPINFO (what the repo uses at `os_windows.go` ~437 and ~806), weaker than CREATE_NO_WINDOW.
c. Tray: `go.mod` has golang.org/x/sys (windows, svc, eventlog) but no go-ole and no systray library. A pure-Go tray needs RegisterClassEx, a hidden CreateWindowEx, `Shell_NotifyIconW` (NIM_ADD, NOTIFYICON_VERSION_4, callback message), TrackPopupMenu, a locked-thread message loop, and re-adding the icon on the `TaskbarCreated` message after Explorer restarts: about 300-400 lines through `windows.NewLazySystemDLL`, no new dependency. Third-party systray libraries add a dependency and are not needed. MS notification-area guidance: new icons start in the overflow and only the user promotes them; provide a way to remove the icon. Icon source: the exe's own `.syso` (RT_GROUP_ICON id 1).
d. Background host options. Windows service: needs admin to install, can start before login, runs in session 0 and cannot show UI to the user (MS Interactive Services page; documented workaround is a hidden GUI helper in the user session over a pipe). HKCU `Run`: no admin, runs at the user's sign-in, the system may delay startup items, 260-char value limit. Startup folder: same timing, no admin, visible to the user (what the repo uses). Per-user Scheduled Task at log on: elevation requirements for creating one are (unverified). All of these show in Task Manager > Startup apps, where the user can disable them.
e. `.lnk` from Go without cgo: COM `IShellLink`+`IPersistFile` needs CoInitialize and go-ole or hand-built vtable syscalls; PowerShell `WScript.Shell` works but spawns PowerShell (AV-noisy); the repo's byte writer already avoids both, keep it. Start menu = Programs / Common Programs (already handled); Desktop = per-user Desktop (can be OneDrive-redirected; resolve with the Known Folder API or the existing user-dir logic) or Common Desktop (admin to write). There is no supported silent taskbar-pin API; a Start menu `.lnk` is pinnable by the user. AUMID matters for toast notifications and taskbar grouping only; plain `.lnk` pins fine (unverified for grouping).
f. Single instance: `CreateMutexW` on `Local\UnravisApp` (Local = per sign-in session, right for a per-user app; Global would block a second Windows user). A second launch must tell the first to open the browser: a hidden message-only window (FindWindowEx + registered message) or a named event. The first instance then mints a fresh launch code and opens the browser. `launch.go` today takes one code at start; it needs a `Rearm()`. A cheaper variant (second process reads session.json and builds a link itself) puts the token in a second process and cuts against A19, so it is not recommended.
g. Defender/SmartScreen: (unverified, general guidance) an unsigned GUI-subsystem exe that hides itself, listens on a port and starts at sign-in resembles malware heuristics; reputation builds slowly. Mitigations: sign (the plan already has a SignPath step for all four exes, `installer-and-releases.md` ~331), keep the visible Startup-folder shortcut instead of a hidden Run key/service for the dashboard, show a tray icon and Quit, no self-copying, no injection. The downloaded setup exe carries Mark-of-the-Web; files the installer writes do not.

## 4. Alternatives
**A. GUI-subsystem unravis.exe + tray + log file (one program does it all)**
- How: build only `unravis.exe` with `-H=windowsgui`. New `internal/tray` (hidden window, menu: Open Unravis, Open log folder, Quit). `Local\UnravisApp` mutex; a second launch from any shortcut signals the first to re-arm a launch code and open the browser, then exits. Fix the MultiWriter so the log file never depends on stderr. `AttachConsole(ATTACH_PARENT_PROCESS)` at start so `--version`, `--help`, `--mcp` from a terminal still work. Fatal startup errors become a MessageBox plus a log line; the "browser failed" link becomes a tray menu "Copy link" instead of stdout. Clean quit: tray Quit, `unravis.exe --quit` over the same window message, WM_QUERYENDSESSION on logoff; setup closeApp asks first, terminates second.
- Files: cmd/audit-explorer (main.go plus new `*_windows.go` and `*_other.go`), internal/tray (new), internal/instance (new), internal/server/launch.go, build.ps1, internal/setup/{plan,layout,uninstall,window_windows,lnk}.go, docs. Size: L (about 8 packets, section 5).
- Pros: one program; visible icon and Quit; no console flash ever; dashboard always findable by MCP. Cons: stdio/console corner cases (a); icon lands in the overflow on Win11; GUI-subsystem unsigned exe looks more suspicious; about 350 lines of Win32 code to own.
- Security/privacy: loopback only, token model unchanged; the window message carries no data, only "open"; mutex and window are per session; the launch link must not be written to the log (it is today when the browser fails).
- Failure modes: Explorer restart (re-add icon), user hides the icon, second-launch signal lost (fall back to a fresh instance after a short timeout), startup errors with no console (MessageBox plus log), logoff/shutdown mid-write.
- Start/stop: shortcut or sign-in starts it; tray Quit stops it. Shortcut = "start if not running, else open the dashboard".
- Scores (10 best): simplicity 6, reliability 7, discoverability 9, security 7, effort 5 = **34**.

**B. Tiny hidden launcher that starts the unchanged console exe with CREATE_NO_WINDOW**
- How: new `cmd/unravis-launch` (GUI subsystem, about 60 lines, same icon) runs the sibling `unravis.exe` from its own folder with `CREATE_NO_WINDOW`, stdout/stderr redirected to a file in the log folder (redirected handles are valid, so MultiWriter and startup lines keep working). Shortcuts and Startup point at the launcher. It checks session.json for a live pid and, if running, opens the browser (needs the same Rearm or a session.json link, see 3f); else it starts the app. Stop: a "Stop Unravis" shortcut (`unravis-launch --stop`) needs a quit hook in unravis.exe (new authorised route or named event), because Ctrl+C cannot reach a console-less process.
- Files: cmd/unravis-launch (new), build.ps1 (build, payload list, manifest), internal/setup (payload name, layout, shortcuts, uninstall), a quit or rearm hook in internal/server or cmd/audit-explorer, docs. Size: M (about 5 packets).
- Pros: unravis.exe, `--mcp`, `--version`, `Start Live.cmd` stay exactly as they are (no console regression, MCP configs untouched); smallest blast radius. Cons: nothing visible while running (Task Manager only) unless a tray is added later (which becomes A); three-level process tree; stale session.json after a kill; a fifth exe to sign; if the child dies at once (port, config) the user sees nothing unless the launcher shows the log tail.
- Security: the launcher must accept no argument that changes what it runs and must never search PATH.
- Failure modes: child crash with no UI, orphaned child if the launcher is killed, launcher/app version mismatch after a partial upgrade.
- Start/stop: shortcut starts/opens; "Stop Unravis" entry or installer close-app (quit hook first, terminate second).
- Scores: simplicity 8, reliability 6, discoverability 3, security 7, effort 7 = **31**.

**C. Always-on per-user agent at sign-in; shortcuts are only openers; no tray**
- How: unravis.exe built as in A (GUI subsystem, mutex, log file, Rearm) and started by the existing Startup-folder shortcut, default on. Desktop and Start shortcuts run `unravis.exe --open`: start the agent if missing, otherwise ask it to open the browser, then exit. Quit = a "Quit Unravis" button in the web UI (new token-authorised POST route) plus `--quit`.
- Files: as A minus internal/tray, plus a quit route in internal/server and a control in `web/`. Size: M-L (about 6 packets).
- Pros: least Win32 UI code; click is instant (agent already up). Cons: nothing visible when the browser is closed (hard to tell it runs or to stop it); relies on the Startup item surviving (if the user disables it, the first click is a cold start, which still works).
- Security: quit route needs the session token, POST, same-origin check. Failure modes: as A minus tray ones.
- Scores: simplicity 7, reliability 7, discoverability 4, security 7, effort 6 = **31**.

**D. Windows service for the dashboard (like keeper/blackbox)**
- How: add a service mode to unravis.exe, installed by setup. A service cannot open a browser or tray in the user's session (3d), so it also needs a per-user helper at logon. It would need a fixed port (today port 0 and a per-run token), and a service account cannot read the user's `%APPDATA%` session/config files or per-user sealed data without a storage redesign. Always needs admin, which breaks the just-for-me install path.
- Files: nearly everything plus data and sealed-storage redesign. Size: L+ (10 or more packets).
- Pros: starts before login, survives logoff, uniform with the two existing services. Cons: wrong security model for a per-user, token-based loopback dashboard; harder upgrade and uninstall; still needs a GUI helper. Not recommended.
- Scores: simplicity 3, reliability 5, discoverability 5, security 3, effort 2 = **18**.

## Recommendation
A, designed so that C is its subset (tray is the last packet and can be dropped). The owner wants to see a shortcut and have Unravis run "somewhere"; a tray icon is the only choice that also answers "is it running, how do I quit". Keep the visible Startup-folder shortcut as the autostart (no Run key, no task, no service for the dashboard); keep keeper and blackbox as they are. B is the cheap fallback but is invisible and still needs a quit hook. D fails on session 0 and per-user data. De-risk A with the first packet: a clean-machine test of a client-spawned `--mcp` and the installer `--version` against the GUI build, plus the log-file fix.
