# WP-74i Profile-link helpers: links inside the user's profile are the user's own process's work
risk: medium    size: M    wave: 2    model: sonnet
## Outcome
This packet states and builds the one approach that closes the "elevated worker writes and deletes links in a user-controlled profile" risk (security review round 2 MAJOR-1, round 3 R3-MAJOR-1). **Approach (stated once; WP-74f, 74g, 74h and 74j refer to it):** when setup runs elevated, the worker never writes, replaces or removes a shortcut whose path is inside the user's profile (`Dirs.UserProfile`). Classify by location: the Desktop link and the Startup link are always window work; the Start-menu link and the Quit link are window work exactly when their path is inside the profile, which is the case for a just-for-me install (they live under `%APPDATA%`). A machine-scope Start-menu and Quit link (in ProgramData, administrator-only) stay in the install transaction. The non-elevated setup window, as the user, creates, replaces or removes the profile links after the worker has committed (WP-74j); silent mode does the same through the same function. A handle-based rewrite of the elevated path was rejected: the transaction and its rollback are path-based, and a user-writable folder under an elevated process is the problem, so the privilege is removed instead of patched.
This packet adds the flag `Runner.NoProfileLinks` (set by the worker), the location test `isProfileLink`, the shared helpers, the in-user functions `WriteProfileLinks` and `RemoveProfileLinks`, and the two shared window-side functions `DeriveStartAtSignIn` and `ApplyProfileLinks` that the setup window and silent mode both call (WP-74j).
Known limits, accepted and not changed here: (1) a just-for-me run that is elevated (Blackbox option, or a leftover service) still writes its program files and state file into the user's profile as administrator; refusing that is a larger rule for a later review. (2) A same-account elevated in-process run (setup started as administrator, `IsAdmin` true) keeps the links in its transaction; the folder check there is check-then-use, and UAC is not a security boundary against the same account.

## Changes
1. `runner.go`: add to `Runner`, with a comment ("set in the elevated worker: it must not write or remove any link inside the user's profile; the window process does that after the worker commits, WP-74i"): `NoProfileLinks bool`.
2. `profilelinks.go` (package `setup`), all names exact:
   - `const startupLinkArg = "--background"` and `const quitLinkArg = "--quit"` (literals, so the installer does not import the app package).
   - `var readLinkFile = os.ReadFile` (the seam tests swap).
   - `func (r *Runner) isProfileLink(path string) bool`: `insideFolder(path, r.Dirs.UserProfile)` (false when either is empty).
   - `func linkTarget(path string) (target string, exists bool, err error)`: `os.Lstat` first (missing -> `exists=false`, nil error; not a regular file, or size over 65536 -> error, and `readLinkFile` is NOT called); then read through `readLinkFile`, then `ReadShortcutTarget`.
   - `func linkIsOurs(path, exe string) (exists, ours bool)`: `ours` only when the file exists, is a regular file (`Lstat`, not a link), parses, and `samePath(target, exe)`; an unreadable or unparseable file is "exists, not ours".
   - `func (r *Runner) refuseLinkedFolder(dir string) error`: check `dir` itself with `r.refuseLink(dir)` and return its error; nothing else (no parent walk: a OneDrive or other redirected parent is a reparse point and is fine; the folder that holds the link is the only one that matters, and a user process only redirects its own writes). A folder that does not exist yet is not an error.
   - **Refusal is a skip, never a failure:** every caller that gets an error from `refuseLinkedFolder` skips that one link and logs `shortcut skipped: <error>`; it does not fail the step or the run.
3. In the same file, the in-user operations (they use no transaction; a failure of one link leaves the others as they are, because each link is independent). Common write: `os.MkdirAll(dir)`, write `<link>.tmp`, `os.Rename` over the link, and on ANY failure after the tmp file was created remove `<link>.tmp` (as WP-74b does for the tray). The shortcut is built as `plan.go` does (Target `l.AppExe`, WorkDir `l.InstallDir`, Icon `l.AppExe`; Description "Unravis", or "Quit Unravis" with Args `quitLinkArg` for the Quit link).
   - `func (r *Runner) WriteProfileLinks(l Layout, startAtSignIn bool, onLog func(string)) error` (`onLog` may be nil): writes, in this order, only the links the window owns: `l.StartMenuLink` and `l.QuitLink` when non-empty and `r.isProfileLink(link)` (replace, as the installer always has); `l.DesktopLink` when non-empty (skip when `exists && !ours` from `linkIsOurs(l.DesktopLink, l.AppExe)`); `l.StartupLink` when `startAtSignIn` (Args `startupLinkArg`; an existing Startup link is replaced, as the installer has always done: the user chose start at sign-in, only the tray toggle, WP-74b, refuses a foreign one). Before writing into each link's folder call `refuseLinkedFolder(filepath.Dir(link))`; on an error `onLog("shortcut skipped: " + err.Error())` and go on with the next link. A write error is remembered, the remaining links are still tried, and the first write error is returned.
   - `func (r *Runner) RemoveProfileLinks(l Layout) []string`: for `l.StartMenuLink` and `l.QuitLink` (only when `r.isProfileLink(link)`), `l.DesktopLink` and `l.StartupLink` (skip empty): `linkIsOurs`; not existing -> nothing; ours -> `os.Remove` (a missing file is not an error); not ours -> kept. Returns one line per problem, "Shortcut <path> (kept: it points to another program)" or "Shortcut <path> (<error>)"; an empty slice when all is well. Read `removeShortcuts` in `uninstall.go` first: if it also removes the Start-menu folder, do the same here with a plain `os.Remove` of that folder after its links (succeeds only when empty; ignore its error) and only when the folder is inside the profile and is not the Programs root itself.
4. `profilelinks_apply.go` (package `setup`): the two functions shared by the setup window (WP-74j) and silent mode (`cmd/unravis-setup`, WP-74j), so the two paths cannot drift.
   - `func (r *Runner) DeriveStartAtSignIn(op Op, saved Options, req *Options)`: `op` is the RESOLVED operation (`ResolveOp(...)`, never the asked one). For `OpUpgrade` and `OpRepair` only: first `req.StartAtSignIn = saved.StartAtSignIn` (`saved` is the options of the existing install, `old.State.Options()`), so the page's value never wins; then `l := NewLayout(saved, r.Dirs)`; `if _, _, err := linkTarget(l.StartupLink); err == nil { _, ours := linkIsOurs(l.StartupLink, l.AppExe); req.StartAtSignIn = ours }`. A read error therefore keeps the SAVED value. Other operations: no change.
   - `func (r *Runner) ApplyProfileLinks(opts Options, res *Result, onLog func(string))`: `opts` is the options of the install: the existing install's for upgrade, repair and uninstall, the request's for a fresh install, with `StartAtSignIn` already set to the value the worker received (`req.Options.StartAtSignIn`). Does nothing unless `res.Outcome` is `OutcomeDone` or `OutcomeLeftovers`. Uses `res.Op` (what actually ran), not the asked operation. `l := NewLayout(opts, r.Dirs)`; for any operation but uninstall, when `res.AppExe != ""` set `l.AppExe = res.AppExe` and `l.InstallDir = filepath.Dir(res.AppExe)` (the exact exe the worker installed, which the worker canonicalised). Uninstall: `lines := r.RemoveProfileLinks(l)` (layout of the old install), append `lines` to `res.Left`, and change `OutcomeDone` to `OutcomeLeftovers` only when `lines` is not empty. Other operations: `if err := r.WriteProfileLinks(l, opts.StartAtSignIn, onLog); err != nil` -> `onLog("shortcut: " + err.Error())` and append "Shortcut (<error>)" to `res.Left` WITHOUT changing the outcome (the done screen shows `Left`, so the user sees the missing link). `onLog` may be nil.
