# Perf sweep: synthetic dataset plan (read-only investigation, 2026-11-04)

## 1. What feeds the three lanes, and the smallest input
- **Hard limits that shape the test.** The tracing route and the UI reject a window over 30 days (`audit.MaxTraceWindow`, `web/src/lib/tracing/windows.ts`). Analysis intervals are at most 7 days (`audit.MaxInterval`). So "3 months" and "12 months" mean the DATASET spans that long and the test slides 30-day (timeline) or 7-day (analysis) windows across it. Test 1/3/12 months as dataset sizes, not as one window.
- **IIS lane** reads case events of importers named `iis-*` (`calltrace.LaneOf`). Real path: `iis-w3c` file. Smallest input: header `#Fields: date time cs-method cs-uri-stem sc-status time-taken` plus lines like `2026-03-10 10:00:01 GET /api/v1/orders 200 45` (fixture: `internal/importer/iis/testdata/w3c_good.log`). Event = `Kind request`, `Start=End=ts`, `DurationMs=time-taken`, attrs `method, stem, status, substatus, win32, client-ip, ...`. The 5xx count (striped bars) comes from `attrs.status`. Needs `TZRule` utc-field (or any rule `traceRuleValidated` accepts) or the lane stays "clock unchecked".
- **SQL lane**: importers `sql-*`. Real, sparse path: `sql-xe` CSV (`timestamp_utc,name,wait_type,duration,...`, fixture `internal/importer/sqlserver/testdata/xe_good.csv`; kinds wait/call/error/deadlock/non-yielding; limit 2M rows, 512 MiB per file). Keep SQL at about 1% of IIS volume (real slow-call logs are sparse).
- **Audit lane**: NOT in the case. It is read live through `audit.RollupReader` (one `Rollup` aggregate per request, `tracing_audit.go`). Store = MongoDB, collection `ApiAuditLog`, fields `RequestInitiatedAt, CreatedOn, ControllerName, ActionName, RequestPollingType, StatusCode, ApiTime, AuditCreateTime, PayloadRecordTime, UserId, UserIp, UserAgent, RequestMainUrl, RequestLengthInKiloBytes, ResponseLengthInKiloBytes, PayrollUIVersion` (`internal/store/pipeline.go`). The demo build uses the in-memory `audit.NewDemo` (2 sources, about 750 rows), which is too small to stress.
  - Cheap Go-level option, no Mongo: a fake `RollupReader` like `auditFake` in `internal/server/tracing_audit_test.go`, filling `audit.NewRollupBuilder(width).AddRow(...)` from the same generator. This stresses merge and wire code only.
  - Full-path option: `docker` (present; no local mongod) running `mongo:7`, the generator bulk-inserts docs, then use the `AUDIT_EXPLORER_TEST_MONGO_URI` convention (`internal/store/mongo_integration_test.go`). `mongosh` is installed too.
- **Case store** (IIS and SQL): SQLite, table `events(evidence_id PK, import_id, source, kind, host, ts_ms, te_ms, duration_ms, value, unit, severity, line, tz_rule, attrs_json) WITHOUT ROWID` plus indexes `ev_ts, ev_kind_ts, ev_import`. Tracing does one `Events()` read per lane (cap 50,000 rows, flagged `rowcap`) and one `CountBuckets` GROUP BY per lane.

## 2. Generator
- **Where**: `internal/perfdata/` (package, importable by tests; today's `internal/perfbench` generators are `_test.go` and cannot be imported) and `cmd/unravis-perfdata/main.go` (writes a case, a manifest and optional raw files). Existing precedent to copy from: `internal/perfbench/bench_gen_test.go` (`genIIS`, uniform spread only), `internal/casestore/sqlite/scale_measure_test.go` (`scaleRun`, direct `Case.Import` with a custom `RunFunc`, no parsing), `internal/server/tracing_test.go` (`seedTracingImport`).
- **Flags**: `--size S|M|L` (preset) or `--months N`; `--end 2026-10-31T00:00:00Z` (start = end minus N months); `--seed 42`; `--iis-rows`, `--sql-rows`, `--endpoints 300`; `--chunk-days 30` (one import per chunk); `--out D:\Projects\api-audit-explorer\.dev\perf-data\<size>`; `--mongo-uri` and `--audit-rows` (optional); `--raw-files` (also write W3C text and XE CSV, small sizes only); `--case-title`.
- **Realism** (all from one `rand.New(rand.NewPCG(seed, day))`, seeded per day so chunks are reproducible and independent): rate curve = business-hour double hump (peaks about 10:00 and 15:00 UTC), weekends at 25%, month-end 1.5x; 2 to 4 bursts a week (5 to 20 min, 8x rate, 30% 5xx); baseline 3% 4xx and 0.4% 5xx; `time-taken` lognormal (median 45 ms), 1% over 2 s, 0.05% over 10 s; 300 endpoints, Zipf-weighted, 40 with ids in the path; SQL waits and calls tied to the same bursts; one 2-hour outage per month with zero rows (gap rendering).
- **Output**: `<out>\cfg\cases\<id>\` (a real encrypted case created with `sqlite.New` + `sealedfile.CurrentUser()`, same as `perfbench.newRig`), `manifest.json` (case id, UTC window, rows per lane per UTC day, burst times, the busiest hour; tests assert bucket sums against it, no second query needed).
- **Sizes** (IIS rows; SQL about 1%; audit docs about 25% of IIS to keep Mongo small):

| Size | Span | IIS | SQL | Audit docs | case.db | Peak extra (WAL) | Gen+import time |
|---|---|---|---|---|---|---|---|
| S | 1 month | 2M | 20k | 0.5M | about 0.85 GB | 1 GB per 2M-row chunk | about 3 to 4 min |
| M | 3 months | 6M | 60k | 1.5M | about 2.6 GB | 1 GB | about 9 to 11 min |
| L | 12 months | 24M | 240k | 6M | about 10 GB | 1 GB | about 35 to 45 min |

  Basis (`docs/superpowers/plans/2026-10-25-performance-notes.md`): 415 B per IIS event on disk (396.6 MiB per 1M), import 9.1k to 11.5k rows/s through HTTP, 12.8k events/s for the store path; the direct path should be at or a bit above that (not measured, measure on S first). Memory is flat while importing (ws 35 to 40 MiB, HeapInuse 10 MiB), so RAM is not the constraint, disk and time are. One import per chunk matters: a single 24M-row import would hold a 10 GB WAL, and the store caps one file at 10M rows by default (`Options.MaxFileRows`). Side effect: several `iis-w3c` imports give the "two selected files use it" ambiguity warning, which a real 12-month history also gives, so keep it and assert it does not break counts. Reading cost to expect: the 50k `Events()` cap is hit in every busy 30-day window, so expect the `rowcap` note and a bucket sum equal to the full row count.

## 3. Using the data
- **Go stress test** (new `internal/server/tracing_stress_test.go`, gated like the others: skip unless `UNRAVIS_STRESS_DIR` is set, plus `-timeout 30m`). Open the generated case with `sqlite.New` on `<dir>\cfg\cases` and the real `CurrentUser` protector, build the handler with `tagEnv(t, store, repo)` (`case_sources_test.go`, `repo` = the fake RollupReader or the Mongo store), then loop `e.json(POST, tracingPath(id), body)` over sliding 30-day windows with `tracingPost` / `tracingLaneOf` / `tracingBucketSum`, the same helpers `TestTracingBucketsExactPastRowCap` uses. Assert per call: status 200; bucket sum and `Scanned` equal the manifest; `Truncated` and `ReasonCode=="rowcap"` when the window holds over 50k rows; wall time under a budget (start with p95 under 5 s on S, record the real baseline first, then set 2x baseline); response bytes under 2 MB (`len(res.Body.Bytes())`); peak `runtime.MemStats.HeapInuse` growth under 300 MB (50k events x 2 lanes x about 1.15 KB is about 115 MB, per the notes) using the `meter` pattern from `perfbench/bench_harness_test.go` (copy `startMeter` or sample every 50 ms). Run 3 parallel requests too (the UI fires one per window change). Analysis: call `/api/analyze` handlers with 7-day windows the same way against the fake or Mongo repo. Command: `$env:UNRAVIS_STRESS_DIR='D:\Projects\api-audit-explorer\.dev\perf-data\S'; go test ./internal/server -run TestTracingStress -v -timeout 30m`.
- **Playwright**: the current launcher (`tools/e2e/support/launcher.ts`) only starts `--demo` with seeded cases, and `UNRAVIS_DEMO_CASES` refuses a config dir that already holds cases. So add `startLive({ configDir })` next to `startDemo`: spawn the live exe with `--no-browser --port 0`, env `AUDIT_CONFIG_DIR=<out>\cfg` (per-user layout, isolated from `%APPDATA%\APIAuditExplorer`), consume the `/launch?c=` link the same way. Work on a COPY of the generated cfg folder per run, because the exe writes to the case. The audit lane is empty in live mode unless a Mongo source is added through the API (docker URI) or a tiny follow-up adds a demo-side switch (a source change, so not done here). Spec `tools/e2e/specs/tracing-perf.spec.ts`: open the case, set the four datetime-local boxes (`fillWindows`, `trace` helpers in `tracing-screen.spec.ts`), click "Start tracing", wait for `.tracing-chart`, assert the answer arrived within the budget (`waitForResponse` timing), count `.bar` nodes per lane stays small (bucket count at most 2000), no console errors, `performance.memory.usedJSHeapSize` under 300 MB after 5 zoom/brush operations. Set `timeout` to 120 s for this spec.
