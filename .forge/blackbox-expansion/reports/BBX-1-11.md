## Finding 1 (HIGH) — all-or-nothing cache guard: FIXED
`resolve_map.go`: the combined `if ierr==nil && serr==nil` guard is gone.
`resolve.go`: `mapLast` split into `mapLastInst` / `mapLastSvc`. Each enumerator
is gated by its OWN baseline and its cached list (`mapInst` / `mapSvc`) is
updated ONLY on its own success. A failure of one never blocks the other and
never forces re-enumeration of the healthy one: on a host with no IIS,
services resolve from tick 1.
- Deliberate reading of "the failed enumerator retries next change": each
  baseline advances with the ATTEMPT (success or failure), so a persistent
  failure retries on the next process-set change, never every tick — this also
  fixes the finding's "both enumerators re-run every tick" footprint complaint
  for the failing enumerator. The cached list still advances only on success
  (last good list kept on error), matching the finding's cache-update rule.
- Test: `TestResolveTargetsIndependentEnumCaches` (2 subtests, both directions:
  pools fail/services resolve AND services fail/pools resolve). Asserts:
  healthy target resolves despite the failure; unchanged set → 1/1
  enumerations (healthy cached, failure waits); set change → 2/2 (failed one
  retries); recovery on next change → both resolve, then cached again.

## Finding 3 (wiring gap) — RunHost never called the resolver: FIXED
`host.go`: RunHost creates `NewResolver()` and wires
`GroupDeps.Targets = func() []ResolvedTarget { rt,_ := resolver.ResolveTargets(cfg.Targets); return rt }`
(only when `len(cfg.Targets) > 0`; with no selected targets it stays nil and
machine-wide groups work exactly as before — zero resolver overhead).
`GroupDeps.ProcessSetChanged` is wired through a new `processChangeGate`
Collector wrapper: it asks `resolver.ProcessSetChanged()` ONCE per collection
cycle and shares that one verdict with every group. Rationale: http, diskCpu
and sqlHost all call the shared func each tick — a consume-on-call func would
let only the first group see a change (the others would never re-expand), and
would snapshot once per group. The gate gives all groups the same verdict and
one snapshot per tick. The gate is primed at startup so tick 1 does not
redundantly re-expand.
- `resolve.go`: new `(*Resolver).ProcessSetChanged() bool` — one snapshot,
  (PID, Start) keys vs the previous call's keys (first call true); NO module
  reads; snapshot error → false (no evidence, never a guess), baseline kept so
  the next good call still detects the change.
- `groups.go`: stale "nil until the resolver is wired" comment updated.
- Tests: `TestResolverProcessSetChanged` (first/stable/added/recycled/removed/
  error-recovery, exactly one snapshot per call, module loader must never be
  called); `TestProcessChangeGateOneVerdictPerCycle` (one snapshot per cycle,
  uniform verdict across 3 group reads, change reaches all groups next cycle);
  `TestRunHostWithSelectedTargetsRecordsCleanly` (nonexistent selected targets
  never stop recording; clean stop). All existing host tests unchanged and
