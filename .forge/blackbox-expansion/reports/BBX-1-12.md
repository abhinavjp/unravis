## What was implemented (packet "Do" items)

1. **`web/src/lib/blackbox.ts`**
   - `Settings` gains `targets: TargetRef[]` where `TargetRef = { kind: 'appPool' | 'service'; name: string }`.
   - `defaultSettings()` now returns `targets: []`.
   - `blackboxApi.targets(signal?)` → `call<TargetsAnswer>('GET', '/this-pc/targets', …)` with the same
     `X-Audit-Token` header as every other method. `TargetsAnswer = { appPools: TargetInfo[]; services: TargetInfo[]; detected: boolean }`,
     `TargetInfo = { name: string; running: boolean }` — names only, matching the BBX-1-10 wire shape.
   - Pure helper `toggleTarget(targets, kind, name)` factored here (no DOM): returns a NEW list, never mutates the
     one given, matches kind+name together, and stores only `{ kind, name }`.
2. **`web/src/components/BlackboxSettings.svelte`**
   - New "Targets (app pools and services)" section between *What to record* and *Keep*.
   - `onMount` calls `blackboxApi.targets()` **once**, guarded by `if (targetMode !== 'pc') return;` — this-PC only,
     no polling (no `setInterval`/`setTimeout`). A late answer after unmount is dropped (`alive` flag).
   - this-PC + detected names → two checkbox lists (app pools, services). Checking adds `{kind,name}` via
     `toggleTarget`; unchecking removes it. A detected target with `running=false` shows the words **"not running"** (never 0).
   - `detected=false`, nothing detected, or pack/remote (`targetMode='manual'`) → manual entry row: kind select
     (appPool/service) + name input + **Add target** button; added names render as removable chips. Enter also adds.
   - Helper line: "Pick the app pools and services to watch in detail. Other counters stay machine-wide."
   - `record.processes` checkbox and its note are byte-for-byte unchanged (guard-tested).
3. **`web/src/lib/copy/blackboxCopy.ts`** — 12 plain string keys (auto-counted, no fixed-count/DRILL_HELP-style key):
   `targetsHeading, targetsHelp, targetsAppPools, targetsServices, targetsNotRunning, targetsKindLabel,
   targetsKindAppPool, targetsKindService, targetsNameLabel, targetsManualNote, targetsAdd, targetsRemove`.
   First-time-investigator wording; lint-clean; no banned terms.
4. **`web/tests/blackbox.targets.test.cjs`** (new) — 8 named tests: toggleTarget add/remove/no-mutate, kind+name
   identity & only-kind+name storage, defaultSettings empty + JSON round-trip keeps targets, `targets()` client
   path/auth via mock fetch, copy lint + count guard, mount-once/this-PC-only/no-poll source guards, "not running"
   wording, and record.processes unchanged.

  two guard regexes were updated to the new signature/invocation. These are structure guards, not the count/lint guards
  the packet forbids breaking; all tests still pass.

No other files touched. No new UI library. No git commit.

## Open questions / unconfirmed

1. **Live-check (packet: YES).** Needs the owner on a real server with IIS: detected pools/services appear and can be
   selected in this-PC mode; a pack install offers manual entry. Logic/shape are covered by the fake tests; the real
   wizard click-through could not be done headlessly here. Compilation (`vite build`, `svelte-check`) and logic
   (`npm test`) are verified; the interactive browser pass is pending the owner.
2. **Rule-2 vs "touch only the packet's files".** The packet's named file list omits the wizard, but rule 2 cannot be met
   without the wizard passing the mode (the Settings component is shared with Apply-settings and has no other signal;
   Svelte 5 forbids a second `$props()`). The minimal one-line wizard change and the two scn1.l8 guard updates are the
   necessary consequence. Flagging for reviewer awareness — if the wizard must stay untouched, rule 2 needs a different
   mechanism (e.g. context) and the packet's file list should be revisited.
3. **Apply-settings default.** The Apply panel (`BlackboxPanel.svelte`, untouched) does not pass `targetMode`, so it uses
   the `'pc'` default — correct, since Apply is always this-PC. Detected targets there are read once on mount as well.
