## What `Decode` does, and why

```go
func (s *requestsSampler) Decode(rows []Row) (any, bool, error) {
	var out []Requests
	truncated, err := decodeRows(rows, &out, CapRequests)
	if err != nil {
		return nil, false, err
	}
	if len(out) == 0 {
		return nil, false, nil
	}
	return out, truncated, nil
}
```

* **It is a decoder, nothing else.** No SQL is built, mutated or parameterised, no statement is chosen here, no
  driver type is asserted, no `context`, no time, no goroutine, no ticker, no mutex (C1/C3/C4/C5/C13). The runner
  resolves `ID()` through `Statement`, sends it under its own budget (`itemLimit(15 s) = quickLimit = 3 s`), and
  calls samplers serially.
* **`decodeRows` is the whole gate and is not re-implemented or widened.** It rejects every column outside the six
  the statement outputs (so `session_id`, `login_name`, `host_name`, `program_name`, `sql_text`, `query_plan`,
  handles, statement offsets, `resource_description`, `physical_name` cannot be decoded even if a driver handed one
  back), validates each wait type against `waitTypeRe`, maps the empty wait type `bb:requests` emits for running
  requests onto `WaitTypeRunning`, and stops at `CapRequests+1` rows (keeps 256, reports `truncated`).
* **The row maps are passed through untouched.** Pre-filtering them in the sampler would be the exact bypass the
  hub forbids; mutant M2 below installs that bypass and the tests kill it.
* **The `''` → `RUNNING` mapping is not duplicated** here (it is inside the requests decode path in `output.go`) and
  `waitTypeRe` is not touched. Mutant M4 re-maps it in the sampler and is caught.
* **Fixed errors only** (C10): the return is exactly what `decodeRows` returned — `errUnknownColumn`, `errWaitType`,
  `errDecode` or `errDst`. Nothing is built from row content, so no column name, value or driver text can become an
  error string, a log line or a payload.
* **Empty → `(nil, false, nil)`** — "nothing is running right now" is *missing*, never an empty array and never a
  zero. `truncated` cannot be true for an empty result (`CapRequests ≥ 1`), so `false` and the hub's
  `nil, truncated, nil` are the same value there; the explicit `false` matches the wave-11-static rule
  "Empty rows -> `nil, false, nil`" and this packet's instruction.
* **No cross-tick state at all**: `type requestsSampler struct{}`. The packet says it plainly
  ("no delta needed (instantaneous)"), so there is nothing stateful to flag and nothing was invented. A group-by of
  *right now* has no baseline to subtract; caching the last reply would only grow memory and would replay rows for
  waits that no longer exist. Mutant M7 adds exactly that and is caught.
* **Surface naming**: the packet's line 10 says `StatementID()="bb:requests"`; the merged `Sampler` interface
  (BBX-5-10, `runner.go`) names that method `ID()`, so `ID()` it is — `Kind()="requests"`,
  `Interval()=BaseInterval` (15 s), registered from `init()` with `RegisterSampler(&requestsSampler{})`.
  `ID`/`Kind`/`Interval` are value receivers (as on the merged `agSampler`); `Decode` is a pointer receiver as the
  hub brief `wave11-A-requests.md` lists it, which the registered pointer satisfies.

## Can only be proven on a real SQL Server (owner, before merging)

1. **Counts match `dm_exec_requests`.** The wait-type task counts, `max_wait_ms`, `blocked`, `head_blockers` and
   `max_block_ms` against a hand-run query on a loaded instance — the self-join's head-blocker count
   (`COUNT(DISTINCT … ISNULL(b.blocking_session_id,0)=0)`) can only be validated against real blocking chains.
   In particular: a blocker whose own row is excluded (`session_id <> @@SPID`) or falls outside the group is counted
   as head, and chains longer than two links are not visible to the join at all.
2. **The RUNNING group equals "running now".** `ISNULL(r.wait_type, N'')` groups every non-waiting request into the
   empty wait type, which the decode maps to `RUNNING`; the sum of the RUNNING group's `tasks` should line up with
   `dm_os_schedulers`' current_tasks minus non-waiting ones — worth one look under load.
3. **Driver value shapes.** `wait_type` is `nvarchar`: the fake rows here use Go `string` and `[]byte` (and
   `decodeRows` converts `[]byte` → string). A real `go-mssqldb` round-trip must produce no `errDecode` for that
   column, and `COUNT(*)`/`MAX(bigint)`/`SUM(int)` must land inside `uint32`/`uint64` (a negative `SUM` would fail
   closed — that is the right behaviour, but only a real instance shows whether it ever happens).
4. **Truncation semantics.** `ORDER BY COUNT(*) DESC` with `TOP 256`: >256 distinct wait types is unlikely, but ties
   in the count make the surviving set non-deterministic between ticks. A real instance must confirm
   `truncated=true` never appears in normal operation, and if it does, that the kept head is still the busiest set.
5. **Query cost inside the 3 s item budget / 5 s tick budget** on a busy instance (the self-join over
   `dm_exec_requests`, `READ UNCOMMITTED`, `LOCK_TIMEOUT 1000`): whether it can ever be the item that eats the tick.
6. **Which session is "own"**: `session_id <> @@SPID` excludes the sampler's session; confirming on a real instance
   that dedicated-admin/b DAC connections and the blackbox's own connection are the only things excluded.
