## Delta / baseline rules implemented

The statement is `SELECT TOP 20 wait_type, wait_time_ms, waiting_tasks_count FROM
sys.dm_os_wait_stats ORDER BY wait_time_ms DESC` — **cumulative since instance start**. `decodeRows`
lands the cumulative pair into `Waits.DeltaMs` / `Waits.DeltaTasks` (the `columnKeys` mapping
`wait_time_ms -> deltaMs`, `waiting_tasks_count -> deltaTasks`); `waitsSampler.Decode` is what turns
them into deltas **in Go**, never in SQL. The previous snapshot lives in a separate private map
`prev map[string]waitsCumulative` keyed by wait type, exactly parallel to `filestatsSampler`'s
`prev map[fileKey]filestatsCumulative`, so the payload struct never carries a cumulative value.

1. **First cycle after startup** records the baseline and emits nothing → `(nil, false, nil)`.
   Two equivalent guards implement it: the `firstCycle := s.prev == nil` short-circuit, and the
   unseen-key rule below (on a `nil` map every key is unseen). Breaking either one alone leaves the
   behaviour intact; breaking both fails the tests — mutation M2/M2b.
2. **Delta** = `current - previous` per wait type, only when the same key had a baseline.
3. **Top-20 churn decision (documented, and the packet's open point):** `TOP 20 ... ORDER BY
   wait_time_ms DESC` means the row SET changes between ticks, so a wait type that left the top 20
   loses its baseline. When it **reappears**, it is treated as *unseen* — baseline only, **no delta
   spanning the gap** — the same rule `filestats` applies to a new file. Rationale: the unobserved
   interval is unknown (one tick or many), so any number computed across it would be a false delta
   attributed to a 15 s window; "missing means missing, never a fabricated value". The cost is one
   silent cycle per re-entering wait type, which is the honest trade.
4. **Counter rollback** (`cum.ms < prev.ms || cum.tasks < prev.tasks`, i.e. instance restart or
   `DBCC SQLPERF(...,'RESET')`): that wait type's baseline is **replaced** by the reset sighting and
   **nothing is emitted for it this cycle**; the next cycle is measured from the reset value. The
   skip is per wait type — healthy waits in the same reply are still reported (asserted).
   `uint64` subtraction never wraps in this path because of the guard.
5. **All-zero delta → dropped, not written as zeros.** Same policy as `filestats`: an idle wait
   type carries no information in a delta series, and `CapWaits` makes payload rows the scarce
   resource (a row of `{"waitType":"X","deltaMs":0,"deltaTasks":0}` is pure overhead). If a wait
   type is present in the top 20 with no movement, its absence from `rows` is meaningful, not a gap.
6. **Empty `rows`** → clears `prev` (a stale snapshot cannot later be subtracted from an unknown
   interval) and returns `(nil, false, nil)`; nothing is fabricated.
7. **Bounded state:** `prev` is **rebuilt** from the cap-limited current rows every cycle
   (`nextPrev := make(..., len(cur))`, then `s.prev = nextPrev`), so `len(prev) <= CapWaits` always —
   keys that fell out of the top 20 are dropped instead of accumulating. Verified across cycles with
   completely disjoint key sets.
8. **Errors:** only what `decodeRows` returns, verbatim, unwrapped, no row content interpolated
   (C10). On error the baselines stay untouched (asserted), because the decode result is discarded
   before any state is written.
9. **Strings:** the wait type is the only string in the payload and is already regex-validated by
   `decodeRows` (`^[A-Z0-9_]{1,60}$`); the mapping is not duplicated, the regex is not loosened, no
   other text is emitted (C9). `''` is **not** mapped to `WaitTypeRunning` here — that sentinel is
   requests-only, and an empty/invalid waits wait type fails the tick with `errWaitType`.

## Needs a real SQL Server (owner check before merging — say so in the PR)

1. **The packet's own live-check item:** wait deltas from this sampler must match perfmon
   `SQL Wait Stats` deltas over the same window (same interval, same instance). Fake rows only prove
   the arithmetic and the guard rules.
2. **Benign-filter cost / duration on a busy instance:** `sys.dm_os_wait_stats` is small, but
   `ORDER BY wait_time_ms DESC` plus the 30-odd `NOT LIKE` predicates were sized by eye. At
   `BaseInterval` the runner gives this item `quickLimit` = 3 s; the owner should confirm the query
   stays well under it (a slow strike backs the whole service off, so an over-optimistic cadence
   shows up as service-wide demotion, not as a waits-only problem).
3. **Reset semantics:** that a restart and `DBCC SQLPERF(N'sys.dm_os_wait_stats', N'RESET')` really
   drive both counters down (never one down / one up in a way the guard misreads), and how often the
   top-20 set actually churns on a real instance — that frequency is what decides whether the
   "re-entry is baseline only" rule is a non-issue or a reason to widen the tracked set.
4. **Wait-type shapes outside the regex:** confirm no live wait type fails `^[A-Z0-9_]{1,60}$`
   (e.g. anything with a digit suffix variant or a NULL). If one did, the tick fails with
   `errWaitType` by design; that should be observed on a real 2016/2019/2022 build, not assumed.
