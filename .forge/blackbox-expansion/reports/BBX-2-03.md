The pre-existing flake that blocked the full-suite gate is fixed. This is a
TEST-ONLY change; no production file was touched (`recorder.go`, `host.go`,
`diskcpu.go` and the rest are unchanged). Only `host_test.go` and `clumsy_test.go`

### The race

`hostRig` drives the real host over an unbuffered `ticks` channel. A send
(`g.ticks <- now`) returns as soon as the recorder's `Run` loop RECEIVES the tick,
but the loop then still has to PROCESS it (`Collector.Collect` → `Store.Append`).
The tests sent ticks and immediately read `/status` (or the manifest) before that
processing finished. With the mandatory real-PDH `diskCpu` group, every tick now
also runs a PDH query, widening the window between "received" and "appended".

In `TestClumsyFullDrivePausesThenResumesAndSaysSoOnTheStatusPage` the second
initial tick was still in flight when `n0` was captured, so `n0` was one short;
the in-flight tick then appended after `disk.set(2)`, giving "disk-low with 3
samples, want 2". It is a synchronization gap, not a logic bug: the same test
failed ~1/8 without the group and ~13/13 with it.

### The fix

A processed-tick barrier was added to `hostRig` (test-only):

- `countingCollector` wraps the rig collector and counts returned `Collect` calls
  (`done`). The recorder loop is sequential, so a returned Collect means that
  tick's append is next.
- `hostRig.tick(t, now)` replaces direct `g.ticks <- now` sends and counts them
  (`sent`). The recorder also takes one sample at once when `Run` starts, so a
  running rig holds `1+sent` samples once every sent tick is processed.
- `waitProcessed(t)` waits until `done >= 1+sent` (all sent ticks collected) and
  then polls `/status` until `Samples >= 1+sent`. `/status` reads the store's
  IN-MEMORY manifest, which `Append` updates synchronously — so the barrier never
  reads the manifest FILE while the recorder is rewriting it (the store persists
  via `os.Rename`, and reading `manifest.json` during that rename fails on Windows
  and freezes the on-disk count). No probe tick is added, so sample counts and the
  assertions' intent are unchanged.
- `waitCollected(t)` is the counter-only variant for the busy-port test, whose
  status server is not listening; that test reads the manifest file itself once
  the ticks are done.

`waitProcessed`/`waitCollected` were inserted before every send-then-read
assertion that depends on tick processing: the full-drive `n0` capture,
`TestRunHostRecordsServesAndStopsCleanly`, the busy-port manifest check,
`TestClumsyReadersCannotChangeOrEscapeTheFolder` (the `seq:1` read) and
`TestClumsyClockMovedFiveSeconds...`. The paused/resume reads in the full-drive
test are already stable (an in-flight paused tick appends nothing), so they need
no barrier. The mid-stream stop test's fast producer loop keeps direct sends (it
never reads state immediately). Assertions are byte-for-byte the same checks
(disk-low pauses sampling; freeing space resumes; one gap caused by disk-low).
