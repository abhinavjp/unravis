## Implementation vs packet

1. `sqlservice.go` constants — `SQLServiceName = "UnravisBlackboxSql"`, `SQLServiceAccount = "NT SERVICE\" + SQLServiceName`, `SQLDataSubdir = "sql"`. `SQLManager{Svc ServiceControl; Env Env}` as specified (plus `DeleteData`, `RevokeScript`, see deviations).
2. `InstallSQL(cfg)` — `cfg.Validate()` → `Env.IsAdmin()` (`msgNoAdmin`, `ReasonNoAdmin`) → `Svc.State(SQLServiceName)` must be `SvcNotInstalled` (`ReasonExists`) → `ensureDir(<cfg.Folder>\sql)` → `SecureSQLDir(dir, sid)` **before** the service exists → `Create(ServiceSpec{Name: SQLServiceName, Args: ["sql-service","--config",<progDir>\blackbox.json], Account: SQLServiceAccount, ExePath: <progDir>\unravis-blackbox.exe})` → `Start` → wait for `SvcRunning`. Failure at any step runs `undoList` in reverse: stop+wait+delete the service, then remove only the folders this call created (a pre-existing `sql` folder keeps its contents — asserted).
3. `RemoveSQL(cfg, confirmName)` — `Validate` → `IsAdmin` → `confirmName != cfg.Name` returns `ErrConfirmName` **before any machine call** → stop (+wait `SvcStopped`) → delete → print `RevokeScript` if set (never executes it) → `os.RemoveAll(<folder>\sql)` only when `DeleteData`. The recordings folder itself and every other file in it are untouched (asserted with a stranger's `notes.txt`).
4. `sqlservice_windows.go` — `sqlServiceSID` (S-1-5-80 + SHA-1 of the upper-case UTF-16LE name, five LE uint32s — the `internal/keeper/owner.go:16` algorithm), `sqlSDDL(sid)` = `D:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;FA;;;<sid>)`, `secureSQLDir` with `PROTECTED_DACL`. Service Create sets `ServiceStartName = SQLServiceAccount` via the new `ServiceSpec.Account`.
5. `sqlservice_other.go` — Windows-only twins.
6. SDDL/SID are pure functions: no ACL is applied by them, and both are tested on every GOOS.

### Deliberate deviations (3, all documented for the reviewer)

- **Pure `sqlServiceSID`/`sqlSDDL` live in `sqlservice.go`, not `sqlservice_windows.go`.** They use only `crypto/sha1`, `encoding/binary`, `unicode/utf16` — no Windows API. Keeping them build-neutral is what lets all six named tests (including `TestSQLSDDLNoUsers` and `TestSQLServiceSID`) compile and RUN under `GOOS=linux` as well as Windows; a `_windows.go` placement would have forced a linux twin plus `t.Skip` on the two security tests. The ACL-applying `secureSQLDir` stays in `sqlservice_windows.go` with its `sqlservice_other.go` twin, as the packet asks. `internal/keeper` cannot be imported (keeper imports blackbox → cycle), so the algorithm is reproduced and cross-checked against Windows itself (below).
- **`ServiceSpec.SIDUnrestricted` added next to `Account`.** The SQL data folder grants the *service SID*, so that SID must be in the service token. This is the repo's own precedent: `internal/setup/system.go:72` ("SIDUnrestricted gives the service its own service SID in its token (the SID the keeper's folder grants)") and `KeeperSpec` (`plan.go:52`) sets `SIDUnrestricted: true` for the keeper's virtual account + SID-granted folder. `WinService.Create` only sets `SidType` when the flag is true, so the host service is unchanged (`mgr.CreateService` skips `updateSidType` for `SERVICE_SID_TYPE_NONE`). Without it the live `icacls`/connect check could fail even though the DACL is correct.
- **Revoke text is a hook, not text owned here.** `SQLManager.RevokeScript string` is printed by `RemoveSQL` (`fmt.Fprintln(os.Stdout, …)`) and never executed; it is empty until BBX-5-02 sets it from its own constant. This keeps the packet's `RemoveSQL(cfg, confirmName) error` signature and keeps all grant/revoke SQL text out of BBX-5-01, as the packet requires ("BBX-5-02 owns the text"). `DeleteData bool` is the "optionally remove the sql folder" switch (the CLI flag in BBX-5-02 sets it).

## Security rules — how each is held

1. **SQL data DACL = SYSTEM + Administrators + SQL service SID only.** `sqlSDDL` is the only source of the SQL folder's permissions; it has no `usersRead` parameter at all, so there is no code path that can add BU/Everyone. Applied with `PROTECTED_DACL` before the service is created. `Env.SecureDir` (the users-readable host lock) is never called by `InstallSQL`.
2. **Own virtual account, not SYSTEM, no stored password.** `Account: SQLServiceAccount` = `NT SERVICE\UnravisBlackboxSql`; `mgr.Config.Password` never set; nothing written to `blackbox.json` or the pack.
3. **The app never grants SQL rights.** No grant/revoke text is executed or even defined here; `RevokeScript` is print-only and owned by BBX-5-02.
4. **Host recordings folder ACL and host service account unchanged.** `InstallSQL` calls only `SecureSQLDir(<folder>\sql)`; `Manager.Install` is untouched; the host spec still has `Account == ""`/`SIDUnrestricted == false`, which `WinService.Create` maps to the previous LocalSystem/no-SidType behaviour. Asserted by `TestInstallSQLLocksFolder` and `TestHostServiceAndFolderUnchangedByTheSQLWork`.
5. **No credentials in blackbox.json/pack.** `Config` unchanged; the SQL service is pointed at the existing config path only.
6. **SQL in a separate service, never inline in the host recorder.** This packet only registers/removes `UnravisBlackboxSql` (same exe, `sql-service` mode, own process). No sampler code changed.

## Open questions / hand-off notes for BBX-5-02 and the reviewer

1. **Wire `SQLManager` to `blackbox.WinService`, not to setup's `bbSvc`.** `internal/setup/plan.go:549-551` (`bbSvc.Create`) copies only Name/DisplayName/Description/ExePath/Args into setup's own spec, so it would silently drop `Account` and `SIDUnrestricted` and run the SQL service as LocalSystem. That file is outside this packet and was not touched. BBX-5-02's `install-sql` command must pass `blackbox.WinService{}` (or the adapter must be extended in that packet).
2. **`sql-service` run mode does not exist yet** (BBX-5-02). Until it lands, `InstallSQL` on a real machine will create the service, fail to start it (unknown command) and undo everything — the intended, safe behaviour, but the owner cannot live-check the service until BBX-5-02 ships.
3. **`InstallSQL` creates missing parents.** If `<cfg.Folder>` does not exist yet, `ensureDir` creates it (and the `sql` child) and only the `sql` child is locked; the parent keeps inherited rights until the host install locks it. No existing ACL is ever weakened. If the reviewer prefers `install-sql` to require an installed host first, that is a one-line guard for BBX-5-02.
4. **Footprint:** 185 new production code lines (166 + 16 + 3) plus 20 changed lines in `service.go`/`service_windows.go`, against the packet's ~150 guide; the rest of the 560 new lines are comments and the 297 code lines of tests. The overage is the undo path, the wait helper and the two pure functions the packet asks for; nothing beyond the packet's surface was added.
5. `RemoveSQL` validates the config before removing (so a drive-root/system folder can never reach `os.RemoveAll`). If a future release lets `probe.enabled` be true, removal of the SQL service would be refused until the config validates — worth remembering in BBX-5-10.
