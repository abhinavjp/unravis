**Exploit / Failure Scenario:**
1. The installer constructs a protected explicit ACL in [internal/blackbox/sqlservice.go:79–84, `sqlSDDL`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/blackbox/sqlservice.go#L79) and applies it through [internal/blackbox/sqlservice_windows.go:14–25, `secureSQLDir`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/blackbox/sqlservice_windows.go#L14).

### W10-03 — Cleanup is disabled exactly when it must reclaim space

**The Flaw:** [internal/bbsql/runner.go:402–425, `checkDisk`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/runner.go#L402) returns before rotation whenever free space is below the floor. `rotate` has no remove-until-free loop. [internal/bbsql/runner.go:251–252, `Tick`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/runner.go#L251) bypasses housekeeping entirely during auto-off. The host does not own SQL files (W10-02).

**Exploit / Failure Scenario:**
1. Old, removable SQL hour files exist. Another workload pushes the volume just below the configured free-space floor.
2. Every SQL tick returns `disk-low` before deleting any expired SQL file. Even after those files age out, the same early return applies.
3. If deleting SQL history would restore the floor but the host has exhausted its own candidates, neither process can reclaim that history. This is a recovery deadlock in control flow, not a mutex deadlock. External deletion/free space is required.
4. An auto-off SQL process likewise leaves all retained files indefinitely. [internal/bbsql/runner_test.go:693–725, `TestFreeSpaceFloorStopsTheTick`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/runner_test.go#L693) only changes a fake free reading from 4.2 to 40; it proves external recovery, not self-reclamation.

**Remediation:** separate housekeeping from sampling authorization. Run safe bounded cleanup while paused/auto-off, re-read free space after removal, and only admit queries/writes after the floor is proven. Distinguish an unreadable volume from a known-low volume, and preserve fixed error codes. Test recovery using only deletion of eligible SQL history, with no external change to the fake disk, plus the case where protected files alone leave the volume low.

### W10-04 — Auto-off is not durably latched when persistence fails

**The Flaw:** [internal/bbsql/runner.go:383–397, `fail`/`saveAndStatus`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/runner.go#L383) discards the persistence result. [internal/bbsql/backoff.go:108–125, `writeFile`/`Save`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/backoff.go#L108) overwrites `state.json` directly, without temp/replace or flush. [internal/bbsql/backoff.go:130–144, `Load`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/backoff.go#L130) treats a missing file as enabled first start.

**Exploit / Failure Scenario:**
1. Disk has a valid enabled state. A permission/ceiling error causes in-memory denied/auto-off.
2. Saving fails before opening/truncating the state file, for example while a Windows handle denies sharing or the file cannot be opened. The old enabled file remains; `fail` silently discards that error.
3. Later ticks can successfully update `status.json` but never retry the authoritative denied state. A restart loads the old enabled state and connects again without owner re-enable.
4. If the first state file was never created, restart follows the missing-file enabled branch. Conversely, a torn in-place write may permanently auto-off a previously healthy service. Power-loss durability is also unproved: neither state nor status is synced.
5. [internal/bbsql/runner_test.go:909–976, `TestStatePersistsAndAutoOffSurvivesRestart`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/runner_test.go#L909) and [internal/bbsql/backoff_test.go:10–27, `fakeDisk`](file:///C:/Users/nachi/Documents/Qoder/2026-11-13/e31b14d4/unravis/internal/bbsql/backoff_test.go#L10) assume successful saves. Valid but incomplete JSON such as `{}`/`null` also passes `Load` and normalizes to enabled; syntactically invalid JSON is the only corruption case tested.

**Remediation:** implement validated, bounded state decoding and atomic durable state replacement, propagate fixed persistence failure codes, and retry a dirty auto-off latch even while sampling is disabled. Distinguish first installation from lost state using a durable initialization/enable protocol. A failed attempt to save denial must never be represented as durable success. Fault-inject failure before open, partial write, close, replace and status update; restart after each and assert zero queries without an explicit successful owner-enable transaction. **Unverified Assumption:** crash/NTFS durability and real sharing behavior require platform fault tests; the swallowed-error/reload path is concrete code behavior.
