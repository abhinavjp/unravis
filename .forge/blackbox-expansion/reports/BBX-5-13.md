## 2. What was built

**`schedulersSampler` — `bb:schedulers`, Kind `schedulers`, `BaseInterval` (15 s).** The statement already SUMs the `VISIBLE ONLINE` rows and has no `GROUP BY`, so SQL answers with exactly one row and `CapSchedulers == 1`. Point-in-time gauge, **no baseline state at all**. Payload is the `Schedulers` **value**, not a slice: `out[0]`, so the NDJSON `rows` field is one object. A one-element array would only invite the analyst to sum a single row again.

**`tempdbSampler` — `bb:tempdb`, Kind `tempdb`, `DemotedInterval` (60 s, see §3).** Also SUMed in SQL (`CapTempdb == 1`), payload is the `Tempdb` **value**. **Emitted raw, not as a delta** — decision and reason: `bb:tempdb` sums `sys.dm_db_session_space_usage`, whose columns accumulate *per session* and disappear when the session ends. The sum therefore moves downwards through a normal day with no reset anywhere, so a Go difference of it would blame or credit one tick for sessions coming and going; the packet's Do-3 asks for "page totals", and "Do not" forbids faked zeros. Consequence: no state to bound here either, which is the cheapest possible sampler.

**`semaphoresSampler` — `bb:semaphores`, Kind `semaphores`, `BaseInterval` (15 s), `CapSemaphores = 16`.** The only stateful sampler in the file: `prev map[int32]semaphoreCumulative`, keyed by the **numeric** `resource_semaphore_id` (never a resource-pool name — C9).

### The gauge-vs-counter table (the part the reviewer must be able to check)

| DMV column | nature | emitted as | why |
| --- | --- | --- | --- |
| `grantee_count` | gauge (instantaneous) | **read as-is** → `grantees` | a grant completing makes it fall; differencing it would report a "negative amount of work" that never happened |
| `waiter_count` | gauge (instantaneous) | **read as-is** → `waiters` | same — a wait ending is not a negative delta |
| `forced_grant_count` | cumulative since start | **`current - prev`** → `forced` | the raw value says nothing about this 15 s window; a memory-grant forced rate is the signal |
| `timeout_count` | cumulative since start | **`current - prev`** → `timeouts` | same — grant timeouts per window |

Rollback is judged **only** on the two cumulative columns (`forced`, `timeouts`); a fall in `grantees`/`waiters` is normal and never treated as a reset. `semaphoreCumulative` records all four values so a baseline is a complete, wholesale-replaceable sighting of the row, but only `forced`/`timeouts` are ever subtracted.

Guards, in the order the code applies them:

1. `decodeRows` gate first — unknown columns return `errUnknownColumn`, nothing is filtered or pre-shaped by hand, `prev` untouched.
2. A row carrying NULL is skipped and **not** baselined, so its counters are never read as zeros; the id re-baselines when it becomes readable again.
3. First cycle (`prev == nil`) records baselines and emits **nothing** (missing is never 0).
4. An id with no baseline (first sighting, or one that had been dropped) is skipped for that cycle — never differenced against a zero baseline, which would fabricate its lifetime total as one window's delta (proven by M12).
5. `current < prev` on either counter → baseline **replaced** by the new reading, **nothing emitted** for that id this cycle; the next cycle measures from the new baseline.
6. A delta that cannot fit the fixed `int32` field is dropped instead of wrapped (`continue`, never a negative "delta").
7. `prev` is **rebuilt** from this cycle's kept rows into a fresh map, so it can never hold more than `CapSemaphores` entries and vanished ids stop costing memory; an empty reply clears the map and returns `(nil, false, nil)`.
8. Rows past the cap are never baselined (they are not decoded), so `len(prev) <= 16` holds even when SQL returns 17.

All-zero counter pairs are still emitted (unlike the filestats/waits samplers): the two gauges beside them describe the grants in flight right now, so a baselined id always carries information; the packet's "don't emit 0" rule is about the *first* sample, which is `nil`.

No goroutines, no timers, no context, no mutex, no driver type assertions, no SQL building, no parameters (C1/C4/C5/C13). Errors are exactly what `decodeRows` returns; no row content is ever interpolated into an error (C10). `schedRowHasNull` only tests `v == nil` — NULL presence, which is how `conn.go`'s `any` scan target reports NULL — not a driver type.

### The NULL / SUM decision (both summed statements)

`SELECT SUM(x) FROM …` with no matching rows returns **one row of NULLs**, not zero rows. `decodeRows` maps a JSON null onto a struct field as a no-op, so that row would silently become `Schedulers{0,0}` / `Tempdb{0,0}` — exactly the "missing reported as 0" defect BL-118 forbids. `schedSummedRowsMissing(rows, cap)` therefore runs before the payload is taken, and reports missing when: there are no rows; a kept row carries no columns at all (a reply that cannot have come from the allowlisted SELECT); or any kept row carries a NULL. Missing → `(nil, truncated, nil)`, and the runner writes `"rows": null`. A genuine `0` total stays a `0` sample (`TestSchedulersMissingNeverZero` pins both directions). Rows past the cap are not inspected — a NULL in a row the reader already dropped is not this sample's business.

## 7. What genuinely needs a real SQL Server (owner, before merging)

Fake rows only prove decode/delta/shape. These need one live instance, and I cannot verify them here:

1. **`bb:semaphores` int32 ceiling.** `forced_grant_count` and `timeout_count` are `bigint` in the DMV, but `Semaphores.Forced`/`.Timeouts` are `int32`, so a cumulative value above 2 147 483 647 makes `decodeRows` return `errDecode` and the runner counts a tick failure (back-off) — pinned by `TestSemaphoresCounterBeyondInt32`, which is a *documented* behaviour, not a desired one. Needs: the largest cumulative value seen on a long-lived instance (a failover-cluster or always-on node with months of uptime and heavy grant pressure can plausibly reach it). Smallest shared-file fix in §8.
2. **Does `sys.dm_exec_query_resource_semaphores` really answer with ≤ 16 rows, in `resource_semaphore_id` order?** Usually 1–3 rows (one per semaphore), but a consolidated-resource / multiple-pool instance can change the set between ticks; the `TOP 16 … ORDER BY resource_semaphore_id` tail cut would then keep a *different* set each cycle and those ids would never form a baseline. Same risk 5-14 flagged for `bb:filestats`.
3. **NULL shape of the SUMs.** Whether an instance with no `VISIBLE ONLINE` scheduler (or no rows in `dm_db_session_space_usage`) returns one row of NULLs as assumed, and what the driver delivers for those NULLs (`nil` in the `any` slot, which `schedRowHasNull` relies on). The `WHERE status = N'VISIBLE ONLINE'` filter is also unverified text-wise — it is in the statement and out of my scope.
4. **`user_objects_alloc_page_count` / `internal_objects_alloc_page_count` semantics.** `sys.dm_db_session_space_usage` reports allocation *accumulated by each session*, which is not the same thing as tempdb space in use right now (`dm_db_task_space_usage`/`dm_db_file_space_usage` are). The sample is honest as "page totals allocated by the sessions currently recorded", but if the owner wants "tempdb pages in use", that is a statement change (BBX-5-05 territory), not a sampler change.
5. **Realistic magnitudes** for the C13 tiers: `budget_test.go` models `schedulers: 1`, `semaphores: 3`, `tempdb: 1` rows — worth confirming against one instance.
6. **Cadence decision of §3** — needs the owner to say which number BL-118 intends now that the runner exists.

## 9. Notes for the SQL reviewer

1. `semaphores` emits a row per baselined id even when both counter deltas are 0 — deliberately different from `filestats`/`waits`, which drop all-zero deltas; here the two gauges are the payload's information. If payload pressure ever matters, dropping the pair `(0,0)` when both gauges are 0 as well is the one-line change.
2. A NULL-bearing semaphore row is skipped *and* un-baselined, so a permanently unreadable column silently produces no data for that id rather than a lie. That is the fail-closed choice; the alternative (a fixed error) would back the whole service off over one column.
3. `grantees`/`waiters`/`forced`/`timeouts` are emitted as `int32` (signed) because the DMV counts can legitimately be 0 and the struct is committed; `schedulers`/`tempdb` counters are unsigned. No field is a `uint` that could have wrapped on a rollback, which is why the rollback guard is `continue` and not a clamp.
4. `semaphoreCumulative` stores all four values but subtracts two. The two gauge fields exist so the baseline is a complete, wholesale-replaceable sighting (and to make the "never difference a gauge" rule visible in the type); they are dead for arithmetic on purpose.
5. The first cycle of `semaphores` emits nothing, so a service started at 03:00 has no semaphore data until 03:00:15 — that is the "missing never 0" rule, not a gap.
