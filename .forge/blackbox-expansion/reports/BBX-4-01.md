## Implementation summary

Follows the http.go group pattern (init RegisterGroup; factory; Collect; OS-independent via injected func):

- `init() { RegisterGroup("events", true, newEventsGroup) }` — optional=true.
- Factory probes `eventsSupported()` (windows: `wevtapi.Load()`; other: error "event log is read only on Windows") and errors on failure so `BuildGroups` skips the group entirely on non-Windows. No query at construction.
- `eventsGroup{query func(since time.Time) ([]rawEvent, error); watermark time.Time}` — the query func is injected; production uses `queryEvents`, tests use fakes (no Windows needed).
- `Collect(now, dt)`: first call sets `watermark = now` (NO historical backfill on restart); queries behind the watermark; `aggregateEvents(rows, watermark)`; advances the watermark to the max TimeCreated seen (held when no rows); returns `*EventsGroup` or `nil, nil` when empty; on query error (e.g. access denied) returns `nil, err` so the collector records `Missing: events` and `Sample.Events` stays nil — never 0.
- `aggregateEvents` (pure): drops rows at/before `since`, groups by (channel, eventID, level), counts, keeps latest T, sorts T desc (deterministic tie-break channel/id), caps at 256 entries.
- `queryEvents` (windows): `windows.NewLazySystemDLL("wevtapi.dll")` with `EvtQuery`, `EvtNext`, `EvtRender`, `EvtClose` (+ `EvtCreateRenderContext`, see note below). Per channel (System, Application): XPath = allowlisted (provider, EventID) pairs AND `TimeCreated[timediff(@SystemTime) <= N]` where N = ms since the watermark; `EvtQueryChannelPath|EvtQueryReverseDirection` (newest first when the cap truncates); `EvtNext` in batches of <=64 with timeout 0, total rows capped at 256 per tick across both channels; every handle closed (`EvtClose` on query, context and each event). `ERROR_NO_MORE_ITEMS`/`ERROR_TIMEOUT` end the stream; any other failure (incl. access denied) is returned as an error.
- NO TEXT: `EvtCreateRenderContext` with exactly three value paths — `Event/System/EventID`, `Event/System/Level`, `Event/System/TimeCreated/@SystemTime` — so `EvtRender(EvtRenderEventValues)` returns only those numeric variants (UInt16 / Byte / FileTime). No message, no EventData, no account names, no process paths, no Computer name ever enters the buffer; `renderEventRow` drops any row whose variants are not the expected numeric types. Channel is the fixed numeric enum from the query loop (1=System, 2=Application), never read from the event. `rawEvent{Channel uint8, EventID uint32, Level uint8, T time.Time}` — no string field exists.
- No goroutine, no ticker, no persistent handle (query opened/closed per tick; 15 s cadence).

Footprint note: the guidance was ~150 lines; the implementation is 318 lines (158+143+17) because the wevtapi FFI needs the lazy-DLL procs, EVT_VARIANT layout, render context, batched EvtNext loop and per-channel cap plumbing, plus the allowlist table and XPath builder. Same precedent as BBX-3-03 (240 vs ~150). No logic omitted to hit the number; no drive-by refactors.

## Open questions / unconfirmed

1. Provider names: the packet's "WAS"/"Resource-Exhaustion-Detector" shorthand was encoded as the canonical `Microsoft-Windows-*` names (required for XPath matching). UNVERIFIED pending the live check; classic disk/Ntfs/volmgr/Application Error/.NET Runtime names are the standard sources.
2. `EvtCreateRenderContext` was added beyond the packet's four listed procs (EvtQuery/EvtNext/EvtRender/EvtClose). It is the only way to make EvtRender return JUST the three numeric fields; without a context, EvtRenderEventValues renders the whole System section (including Computer/provider strings). This is the strictest reading of the no-text rule.
3. Line budget: 318 implementation lines vs ~150 guidance — wevtapi FFI plumbing (procs, EVT_VARIANT, render context, batched EvtNext, per-channel cap) plus the allowlist/XPath/aggregation; same precedent as BBX-3-03. No logic omitted.
4. An event whose Level element is absent renders as a Null variant and is recorded as Level 0 (win:LogAlways semantics); EventID/TimeCreated missing or non-numeric drops the row. Worth a glance at the live check.
5. Per-tick query cost on this dev box (~650-700 ms, 0 rows) is under the 1 s group budget but not trivial; confirm on the real server. If it proves slow there, the budget's slow-group skip already protects the tick.
