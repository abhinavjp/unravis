## Findings fixed

### 1. HIGH — CPU unit mismatch (percent-of-machine vs percent-of-one-core)
`SelfUsage` divided the CPU delta by `CoreCount()`, so on an N-core server a
recorder burning a full core reported 100/N % — under the 0.5 threshold on any
machine with >200 cores, and badly diluted everywhere; the CPU budget could
never fire as intended. `Budget.SelfUsage` expects percent of ONE core
(1 full core = 100, threshold 0.5).

Fix in `internal/blackbox/selfstat_windows.go`:
- Removed the `/CoreCount()` division.
- Factored the math into a pure helper
  `cpuPctOfOneCore(cpuDelta100ns, wallSeconds float64) = delta/1e7/wall*100`
  (no core division), used by `SelfUsage`.
- Corrected the doc comment (it previously described the wrong unit).
- Renamed the named return identifier `cpuPctOfOneCore` → `cpuPct` so it does
  not shadow the new helper (signature types unchanged).
- Working-set trigger unchanged (`wsBytes` from `K32GetProcessMemoryInfo`,
  same `ok=false` paths). `CoreCount()` kept (still used by `GroupDeps.Cores`).

New test `internal/blackbox/selfstat_windows_test.go` (windows build tag):
`TestCPUPctOfOneCore` — table: 1 core-second over 1 s = 100 (the named case),
0.5 core-second = 50, 1 core-second over 2 s = 50, threshold 0.5, two
saturated cores = 200 (proves no machine-wide normalization).

### 2. MEDIUM — widening fabricated running-late + false gaps
`Status` judged lateness with the base `Config.IntervalSeconds` and
`Store.Append` computed gaps with the base `StoreOptions.IntervalSeconds`,
while `Run` ticks at the budget's EFFECTIVE interval. At effective 60 / base
15 every sample looked late (60 > 3×15) → false `Gap` + `running-late`.

Fix (smallest correct route — a store interval setter; `Append`'s signature
and all its existing call sites/tests are untouched):
- `internal/blackbox/recorder.go` `Status`: `IsLate(ref, now,
  effectiveInterval(r.o.Budget, r.o.Config.IntervalSeconds))` — base when
  Budget is nil (reuses the existing `effectiveInterval` helper).
- `internal/blackbox/store.go`: new `gapInterval` field, initialized to
  `opt.IntervalSeconds` in `OpenStore`; new `SetInterval(seconds int)`
  (mutex-guarded, ignores <= 0); `Append`'s `GapBetween` now uses
  `s.gapInterval`. The manifest's `IntervalSeconds` keeps the configured base
  (the offline reader's state math is a separate concern, unchanged).
- `internal/blackbox/recorder.go` `Tick`: after `feedBudget()` (which may
  widen), when `Budget != nil` calls
  `Store.SetInterval(effectiveInterval(...))` — O(1), no new goroutine/ticker,
  the `o.Ticks` test path is unchanged.

New tests in `internal/blackbox/recorder_test.go`:
- `TestWidenedBudgetNoFalseGapOrLate` — real Budget widened 15→30→60, samples
  60 s apart: 3 samples, NO gap, `Status == "running"` (also at +60 s past the
  newest sample). Fails on the pre-fix code (60 > 45 → gap + running-late).
- `TestBaseIntervalStillDetectsRealGap` — base 15, no budget: a real 60 s hole
  reads `running-late` and is recorded as one 60 s `late` gap.

## Fix round 2 (re-review: two problems the round-1 fixes introduced)

A re-review confirmed the round-1 fixes but found two new problems. Both are
fixed here; they resolve the two "Notes / unconfirmed" items above.

### PROBLEM 1 (HIGH — data race) — FIXED
`Recorder.Status()` reads `Budget.EffectiveInterval()` from the status server's
HTTP goroutines (`server.go handleStatus`) while the tick goroutine writes
`Budget.effective` via `Cycle → widen/stepBack`. `r.mu` does not cover Budget.
- `budget.go`: `effective` is now an `atomic.Int64`. `EffectiveInterval()` does
  an atomic `Load`; `widen`/`stepBack` do atomic `Store`; `NewBudget` stores the
  base atomically. All other Budget fields stay tick-loop-only (single writer).
  The type doc now states `EffectiveInterval` is safe for concurrent reads.
- No value copies of `Budget` exist (always `*Budget`), so `atomic.Int64`'s
  `noCopy` is respected and `go vet` copylocks stays clean.
- `TestBudgetCycleAllocatesNothing` still passes: atomic Load/Store allocate 0.
- New test `TestBudgetEffectiveIntervalConcurrentReads` (budget_test.go): one
  tick goroutine widens/steps back while 8 reader goroutines hammer
  `EffectiveInterval`, asserting every read stays within the ladder [15,60].

### PROBLEM 2 (MEDIUM — false running-late in offline reader) — FIXED
`state.go DeriveState` judged lateness against the manifest BASE interval
(`m.IntervalSeconds`), so a budget widened to 60 s (base 15) made on-time 60 s
samples look late for part of each cycle.
- `manifest.go`: added `EffectiveIntervalSeconds int` with
  `json:"effectiveIntervalSeconds,omitempty"`; base `IntervalSeconds` unchanged.
  `omitempty` keeps older manifests and zero-value round-trips byte-identical.
- `store.go SetInterval`: now also persists `s.m.EffectiveIntervalSeconds` and
  rewrites the manifest only when the value changes (no extra per-tick write at
  a steady cadence). `gapInterval` behavior is unchanged.
- `state.go DeriveState`: prefers `m.EffectiveIntervalSeconds` when > 0, else
  falls back to `m.IntervalSeconds`, else `DefaultIntervalSecond`. That interval
  flows into `isLate` (> 3×interval) and the "Recording every N seconds" detail.
- New tests:
  - `TestLatenessUsesEffectiveIntervalWhenWidened` (state_test.go): effective
    60/base 15 with an on-time 60 s sample → `SRunning`; no effective field →
    base 15 behavior (60 s → `SRunningLate`); a 181 s sample at effective 60 is
    still `SRunningLate` (lateness not disabled).
  - `TestStoreSetIntervalPersistsEffectiveInterval` (store_test.go):
    `SetInterval(60)` persists effective 60, base stays 15, survives
    `ReadManifest`; `SetInterval(0)` is ignored.
