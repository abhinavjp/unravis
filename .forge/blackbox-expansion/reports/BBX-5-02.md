## Design decisions

- **Pinned requirement applied**: `realDeps().sqlMgr = &blackbox.SQLManager{Svc: blackbox.WinService{}, Env: blackbox.OSEnv{}}` — NOT `internal/setup/plan.go`'s `bbSvc` adapter (which copies only Name/DisplayName/Description/ExePath/Args and drops `Account`/`SIDUnrestricted` → LocalSystem). `internal/setup` was not modified. `TestInstallSQLSpecAccountAndSID` asserts both the recorded spec (`Account = NT SERVICE\UnravisBlackboxSql`, `SIDUnrestricted = true`, folder locked to the S-1-5-80 service SID) and that `realDeps().sqlMgr.Svc` is `blackbox.WinService` by type assertion (works on both platforms).
- **Runner stub**: BBX-5-10 (`internal/bbsql` runner) has not landed (only allowlist.go/backoff.go exist). `deps.sqlRun` defaults to `runSQLStub`, which opens no connection, runs no SQL, starts no server, logs one fixed line and waits for ctx cancellation. BBX-5-10 replaces the stub via the `sqlRun` seam; the mode/handler stay.
- **Revoke printing**: `SQLManager.RevokeScript` is left empty ("empty prints nothing" per BBX-5-01) and `remove-sql` prints the script through the answer writer instead — so it is captured in text AND JSON modes (`revokeScript` field) and never bypasses `--json` by writing to os.Stdout.
- **`deps.elev` canary**: the CLI is itself the elevated helper and never elevates further. The field stays nil in `realDeps` (any accidental future use panics — fail closed); tests inject `fakeElev` to record that install-sql/remove-sql/sql-service never call it.
- **Config source**: `install-sql`/`remove-sql` read the installed `blackbox.json` (same pick logic as other commands); missing config → fixed `not-installed` reason. `remove-sql` always requires `--confirm-name` (SQLManager semantics); SQL data is kept (no delete-data flag added — not in packet).
- **Hidden mode**: `sql-service` is not in the usage text. `sqlServiceEntry` runs before `serviceEntry` so an SCM-started SQL process can never fall into the host handler; console `sql-service` runs the same code in the window (Ctrl+C stops).

## Security fix round (Ultimate review: 1 MEDIUM + 1 LOW)

### FINDING 2 (MEDIUM) — service config divergence left an unlocked folder
`install-sql --config <path>` locked `SQLDataDir(cfg.Folder)` from THAT config but registered the service with a hardcoded `--config = progDir/blackbox.json`, so the service could read a DIFFERENT, never-locked folder (SQL data world-readable).

Fix (the simplest correct route): `SQLManager.InstallSQL(cfg Config, configPath string)` now takes the exact config path the caller validated `cfg` from and registers the service with that same path — no hardcoded `progDir` divergence. `SecureSQLDir` is applied to `SQLDataDir(cfg.Folder)` of that same `cfg`, which is exactly the folder the service will use (it reads `configPath`). An empty `configPath` is refused (`ReasonOther`) before anything changes. `cmd/unravis-blackbox/main.go` passes `paths.ConfigPath` (the picked/validated path) through.

### FINDING 4 (LOW) — revoke only named the 2022+ right
`revokeScript` now prints `REVOKE VIEW SERVER PERFORMANCE STATE` plus a commented `-- REVOKE VIEW SERVER STATE FROM [...]` alternative for SQL 2019 and older (which have no PERFORMANCE STATE right), so the owner revokes whichever was granted. Still print-only, never executed.
