## What was built
- **One tick at a time (C4).** `Tick` sets `running`, and a tick that arrives while one is in flight returns `nil` after `skipped++`: ticks never queue and never overlap. The whole tick runs under `context.WithTimeout(ctx, 5s)` on the **real** clock (not the injected `Now`), and each item gets `min(itemLimit, remaining)` — 3 s for 15 s items, 5 s for 60 s items. When the tick budget is spent the sampler loop breaks; the rest waits for the next tick.
- **One connection (C5), re-proven every connect (C8).** `reconnect` opens through `Connect` (nil → `defaultConnect` → `Open`, which keeps `max open 1`) and runs `CheckCeiling` **before** any sample statement. Any failure calls `dropConn`, so rights changes are caught at the next connect, not at service start.
- **Allowlist only (C1).** Every send goes through `Statement(s.ID())` → `Query`, which refuses anything not exactly on the list. A sampler with an unknown id fails closed with the existing `CodeNotAllowed`, and nothing is sent for it.
- **Back-off and auto-off (C7).** One `OnSuccess()` per tick, not per sampler (per-sampler would undo the halving inside a single tick). `OnFailure` classification: permission / login-failed / too-many-rights → `denied` + auto-off immediately; ten failures → `auto-off`. Auto-off is persisted and re-read by `NewRunner`, and `Tick` short-circuits to a status write when it is set — no statement is ever sent. `OwnerEnable` is the only path back.
- **Fixed outputs (C9/C11).** `SampleDoc` is `{v,t,kind,truncated?,rows}` with `truncated` omitted when false; `StatusDoc` is exactly `{enabled,state,lastOK,failures}`, written temp-file + rename so the host never reads a half-written file.
- **Fixed errors (C10).** `fail` classifies, persists only state, and logs/returns only the fixed code. The raw error is dropped; nothing driver-shaped reaches disk, the log or the return value.
- **`Gate` seam (new, needed by BBX-5-14).** An optional `GateID()/GateOpen(rows)` interface: the runner sends the gate statement first, and when `GateOpen` is false the sampler's own DMV statement is never sent for that tick while `lastRun` still advances, so a closed gate is re-checked on the sampler's cadence rather than spinning. An **unreadable** gate (timeout, query failure) stays closed and is **not** counted as an instance failure; a **refused** gate (permission/login/too-many-rights) still fails the tick, because that is a rights problem, not a missing feature.
- **Retention and free space (new — was missing from the hub output).** The SQL service writes its own folder and host housekeeping never looks inside `\sql`, so the runner now owns it: `rotate` deletes `bb-sql-<hour>.ndjson` files older than `KeepHours` (default 168 h = 7 days, same window as the host's `keepDays`), at most one directory sweep per hour, and leaves any name that is not exactly one hour alone (`validHour`, length-gated so `bb-sql-20260304-5.ndjson` can never be deleted). `checkDisk` compares the drive against the owner's `MinFreePercent` floor before connecting and returns the fixed `disk-low` code, writing nothing — deliberately not a SQL failure, because `State` tracks the instance, not the drive.
- **Service wiring.** `runSQLServiceLoop` makes the folder, builds `NewRunner(o.Dir, sqlConnConfig(...))` with `(local)` only (C12), `QueryTimeout: 5s`, and the three trust-anchor fields; `main.go` now uses it instead of `runSQLStub`.

## Defects found in the Hub output and fixed here
1. `var _ sql.DB` import hack, and a deadline built from the **fake** clock mixed with real `time.Until` — the budget would not have stopped anything.
2. `OnSuccess()` called per sampler — one good tick would have collapsed the back-off.
3. `fail(err, ctx, _, _ bool)` with dead parameters, and `used` measured against the **unclamped** limit (slow strikes would be miscounted).
4. No `Gate` seam at all — BBX-5-14's AG sampler would have queried an AG DMV on every Standard-edition instance.
5. **No retention and no free-space control** — unbounded growth in `\sql`, i.e. a disk-filling hazard on a production server.
6. `used`/payload assertions conflated wall time with CPU time (see C13 below).
7. Hub test fixtures keyed rows by JSON names (`databaseId`) instead of SQL column names (`database_id`); `decodeRows` rejects those, so those tests could never have exercised the samplers. Fixed in both the budget and filestats fixtures.
8. `TOP n` without `ORDER BY` in 5 allowlisted statements — with a cap and no deterministic order, two ticks can return **different row sets** for the same query, which silently corrupts every Go-side delta baseline. `ORDER BY COUNT(*) DESC` / `resource_semaphore_id` / `database_id, file_id` / `database_id` / `permission_name` added. **This is a real design bug the review caught, not a test bug.**

## C13 footprint — measured on this machine (Core Ultra 9 185H, Windows, NDJSON on NTFS with AV)
Two tiers, because "1% of one core" and "2 KB per sample" describe a healthy instance, not a saturated fixture:

| tier | process CPU / tick | wall / tick | allocs / tick | mean line | max line | worst tick |
|---|---|---|---|---|---|---|
| realistic (14 waits-in-use, 40 files, 8 AG dbs) | **25.8 ms** (cap 150 ms) | 155 ms | 174 KB, 2 867 allocs | **680 B** (cap 2 048 B) | 4 463 B | 7 826 B |
| at-cap (256 requests, 256 files, 16 semaphores, 64 AG) | 35.2 ms | 918 ms | 1.32 MB, 20 195 allocs | 3 550 B | 29 556 B | 59 421 B |

- **CPU is the right metric and it passes with margin.** Wall time is dominated by file I/O: a scratch measurement put `appendSample` at ~11 ms, `writeStatus` ~14 ms and `Save` ~8 ms per call on this host, which explains 155 ms of wall for 26 ms of CPU. The gate now asserts CPU (via `GetProcessTimes` / `Getrusage`) and logs wall without judging it.
- **The 2 KB claim holds on the mean (680 B) but not per group**: one `filestats` line on a 40-file instance is **4 463 B**, because `FileStats` carries 7 numbers × 40 files. Owner decision needed: keep the cap (256 files → 29 KB) and read "2 KB" as the mean, or shrink `TOP 256`/split the group.
- **Worst-case storage**: an at-cap tick is 59 421 B → ~342 MB/day if *every* tick were saturated, ~2.4 GB across the 168 h retention window. The realistic tier is ~3.2 KB/tick → ~55 MB/day, ~385 MB retained.
- Goroutines: 2 → 2 across 20 ticks; one hourly file per hour; the closer is never called on a successful tick and exactly once when a tick fails or `Run` exits.

## Open questions for the Ultimate gate
- `Gate` semantics: unreadable gate → closed and **no failure counted**; refused gate → fails the tick. Chosen so an absent feature cannot auto-off the service while a rights regression still stops it.
- `defaultKeepHours = 7*24` for `\sql` — matches the host `keepDays` window; `MinFreePercent` is only enforced when the caller installs a `FreePercent` reader (the host recorder holds the real gate today).
- `KeepHours`/`MinFreePercent`/`FreePercent` are struct fields, not config: the service mode does not set them yet (owner's floor lives in host config). Wiring them is a follow-up, not part of this packet.
