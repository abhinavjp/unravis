### bb:requests (BL-101)
```sql
SET NOCOUNT ON; SET LOCK_TIMEOUT 1000; SET DEADLOCK_PRIORITY LOW; SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; SELECT ISNULL(r.wait_type, N'') AS wait_type,
  COUNT(*) AS tasks,
  MAX(r.wait_time_ms) AS max_wait_ms,
  SUM(CASE WHEN r.blocking_session_id > 0 THEN 1 ELSE 0 END) AS blocked,
  COUNT(DISTINCT CASE WHEN r.blocking_session_id > 0 AND ISNULL(b.blocking_session_id, 0) = 0 THEN r.blocking_session_id END) AS head_blockers,
  MAX(CASE WHEN r.blocking_session_id > 0 THEN r.wait_time_ms ELSE 0 END) AS max_block_ms
FROM sys.dm_exec_requests AS r
LEFT JOIN sys.dm_exec_requests AS b ON b.session_id = r.blocking_session_id
WHERE r.session_id <> @@SPID
GROUP BY ISNULL(r.wait_type, N'') /* unravis:bb:requests */
```
Output: wait_type, tasks, max_wait_ms, blocked, head_blockers, max_block_ms (matches BBX-5-09 `Requests` struct). session_id appears only in WHERE/JOIN, never in output.

## Design decisions / deviations (reviewer please confirm)

1. **C2 token-scan semantics (important).** A naive case-insensitive *substring* scan over the whole text is incompatible with the packet's own required statements: `sys.dm_exec_requests` / `sys.dm_exec_query_resource_semaphores` contain `exec`; `grantee_count` / `forced_grant_count` contain `grant`; and the mandated benign filter contains the literals `N'WAITFOR'` and `N'SP_SERVER_DIAGNOSTICS_SLEEP'` (`waitfor`, `sp_`). The lint therefore uses:
   - **Exfiltration column tokens** (sql_text, dm_exec_sql_text, query_plan, input_buffer, _handle, statement_, resource_description, program_name, host_name, login, physical_name, master_files, availability_replicas): case-insensitive **substring** over the FULL text (strictest).
   - **Statement/execution keywords** (EXEC, sp_, xp_, INSERT, UPDATE, DELETE, MERGE, ALTER, CREATE, DROP, GRANT, DBCC, KILL, OPENROWSET, WAITFOR): case-insensitive **word-boundary** match over the text **with string literals removed**, so wait-type *data* is not mistaken for a WAITFOR statement / sp_ proc, and `dm_exec_*` / `grantee_count` are not mistaken for EXEC / GRANT. EXEC/sp_/xp_ use a leading boundary (also catches EXECUTE / sp_who). Negative controls in `TestLintC2` prove real `EXEC sp_who`, `WAITFOR DELAY '...'`, `sql_text`, `program_name`, `login` injections are still flagged. This is a deliberate, security-preserving interpretation of "substring scan"; flagging for Ultimate (SQL) sign-off.
2. **Tag format:** `/* unravis:` + id + ` */` → `/* unravis:bb:requests */` (the id already carries the `bb:` namespace; no doubled `bb:bb:`).
3. **bb:requests head-blocker count** uses a single self-LEFT-JOIN (`b.session_id = r.blocking_session_id`) + `COUNT(DISTINCT CASE ...)` so it stays exactly one SELECT (no subquery). A blocker absent from `dm_exec_requests` (e.g. sleeping with an open tran) is treated as a head blocker. Minor edge: under MARS a session can have >1 request row, which could multiply joined rows; acceptable for a count, noted for the live check.
4. **bb:requests empty wait type:** `ISNULL(r.wait_type, N'')` yields `''` for running (non-waiting) requests. BBX-5-09's wait-type regex `^[A-Z0-9_]{1,60}$` rejects `''`. Integration note for BBX-5-09/5-11: map/skip the empty wait type (a regex-safe sentinel such as `NONE` could be substituted here if the reviewer prefers). Left faithful to "GROUP BY wait_type" for now.
5. **bb:filestats `size_on_disk_bytes`:** selected because BBX-5-05 explicitly lists it, but BBX-5-09's `FileStats` struct has no matching field and `decodeRows` rejects unknown fields. Downstream (5-09/5-14) must add the field or drop the column. Flagged, not changed here.
6. **bb:filestats TOP 256 has no ORDER BY** (matches both BBX-5-05 and BBX-5-14 literally); the 256 rows are therefore unspecified order. Open question: add `ORDER BY io_stall_read_ms + io_stall_write_ms DESC` for determinism?
7. **bb:ag has no `is_local` filter** (matches BBX-5-14 literally); returns one row per replica per database. Open question: filter `is_local = 1`?
8. **bb:hadr guard NOT added here** — BBX-5-14 owns adding it. Tests are forward-compatible: lint iterates the whole `Statements` map, there is no `len==7` assertion, and `bb:hadr` is not listed as an unknown id.
9. **Footprint:** 322 lines total (92 + 230) vs the packet's "~150" estimate. Driven by 7 full statements (incl. the 11-line reused benign filter) + 5 named tests + a real C2 scanner + an output-column parser. No extra files, no refactors.
