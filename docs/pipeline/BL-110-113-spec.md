## 3. BL-110 step 1: `diag-probe` (read-only test tool), in full

### 3.1 Behaviour

`unravis-blackbox diag-probe --pid N [--seconds S] [--start-ticks T] [--json]`

One run does exactly this, in order:
1. Check N is a plain process id: not 0, not this process, fits uint32.
2. Windows: open the process with `PROCESS_QUERY_LIMITED_INFORMATION` only, read its creation time, check it is still running. If `--start-ticks` was given and differs: refuse (`peer-mismatch`).
3. Connect to the diagnostic port of N (Windows: `\\.\pipe\dotnet-diagnostic-N`; Linux: the socket, section 3.4).
4. Before any byte is written: check that the server of that pipe is process N. If not, close, write nothing, stop (`peer-mismatch`).
5. Send ONE fixed message: `CollectTracing3` with the fixed counters request (3.3). Read ONE reply (28 or 24 bytes).
6. Read the stream for S seconds (default 20, allowed 5-60). Count bytes. Keep only the first 128 bytes, only to check the 102-byte nettrace preamble. Everything else is read and thrown away.
7. Open a SECOND connection (same checks as 3-4, and the creation time must equal the one read in step 3). Send ONE fixed message: `StopTracing` with the session id. Read ONE reply. Close it.
8. Drain the first connection to end of stream for at most 5 s, counting bytes, then close it.
9. Print the result and exit with the fixed code (3.6).

It sends no command other than those two. It writes no file. It prints no stream bytes, no provider text, no command line. Ctrl+C runs steps 7-8 before exiting. A panic runs step 7 too (deferred).

The probe is not part of the service and the service never calls it in step 1.

```go
package dotnetdiag

type Reason string // fixed words only; never OS or runtime text
const (
	ReasonNotRunning   Reason = "not-running"
	ReasonDenied       Reason = "diag-denied"
	ReasonDisabled     Reason = "diag-disabled" // no port open in a live process
	ReasonBusy         Reason = "busy"
	ReasonPeerMismatch Reason = "peer-mismatch"
	ReasonUnsupported  Reason = "unsupported"
	ReasonRejected     Reason = "rejected"   // runtime sent an error reply
	ReasonTimeout      Reason = "timeout"
	ReasonBadReply     Reason = "bad-reply"
	ReasonBadStream    Reason = "bad-stream"
	ReasonStopFailed   Reason = "stop-failed"
	ReasonCancelled    Reason = "cancelled"
	ReasonOther        Reason = "other"
)

// Error carries a Reason and a number (Win32 error or HRESULT, 0 if none).
type Error struct { Reason Reason; Code uint32 }

type Target struct{ PID uint32; StartTicks int64 } // StartTicks 0 = no expectation
type Peer   struct{ PID uint32; StartTicks int64 } // what the dialer verified

type Conn interface { io.ReadWriteCloser; SetDeadline(time.Time) error }

// Dial opens ONE connection. Before it returns, it has checked that the server
// of the connection is process t.PID and, when t.StartTicks != 0, that the
// process was created at t.StartTicks. On any failed check it closes the
// connection and returns ReasonPeerMismatch. It has written no byte.
type Dialer interface { Dial(ctx context.Context, t Target) (Conn, Peer, error) }
func DefaultDialer() Dialer

type Options struct {
	Duration     time.Duration // default 20 s, allowed 5 s..60 s
	ReplyTimeout time.Duration // default 5 s
	StopTimeout  time.Duration // default 5 s (connect + reply, and the final drain)
	StreamCap    int64         // default 4 MiB read in total, then stop early
}
func Probe(ctx context.Context, d Dialer, t Target, o Options) (Result, error)
```

### 3.3 Wire format (exact bytes)

All numbers little-endian. Strings are `uint32 length-in-chars incl. NUL` + UTF-16LE with a final 0 char. `bool` is 1 byte.

Header, 20 bytes: `"DOTNET_IPC_V1\0"` (14 bytes, includes the NUL) + `uint16 size` (header + payload) + `uint8 command_set` + `uint8 command_id` + `uint16 reserved = 0`.

Start message, `CollectTracing3` = set `0x02`, id `0x04`. Payload:

| Field | Value | Bytes |
|---|---|---|
| circularBufferMB | 1 | 4 |
| format | 1 (NetTrace) | 4 |
| requestRundown | false | 1 |
| requestStackwalk | false | 1 |
| provider count | 1 | 4 |
| keywords | `0x00000000FFFFFFFF` | 8 |
| logLevel | 5 (Verbose) | 4 |
| provider_name | `System.Runtime` (15 chars incl. NUL) | 4 + 30 |
| arguments | `EventCounterIntervalSec=5` (26 chars incl. NUL) | 4 + 52 |

Total 136 bytes (`size` = 0x0088). Golden hex (generated by a scratch program today, to be pinned in `TestEncodeStartGolden`):

```
444f544e45545f4950435f5631008800020400000100000001000000000001000000ffffffff00000000050000000f000000530079007300740065006d002e00520075006e00740069006d00650000001a0000004500760065006e00740043006f0075006e0074006500720049006e00740065007200760061006c005300650063003d0035000000
```

Why this setting: it is what `dotnet-counters` itself asks for (Verbose, all keywords, `EventCounterIntervalSec`), so the probe tests the known-good path first. Only `System.Runtime` is used in step 1: `Microsoft.AspNetCore.Hosting` also has request events with the request path as text, and keywords 0xFFFFFFFF would turn them on. Narrowing level and keywords for the Hosting provider is a step-3 question (open question Q-lvl, section 8). The probe discards payload bytes, so no text can be stored anyway.

Stop message, `StopTracing` = set `0x02`, id `0x01`, size 28, payload `uint64 sessionId`. Golden for session id `0x1122334455667788`:

```
444f544e45545f4950435f5631001c00020100008877665544332211
```

Replies the client accepts. Anything else is `bad-reply`:

| Reply | Size | set | id | Payload |
|---|---|---|---|---|
| OK for Collect and Stop | 28 | `0xFF` | `0x00` | `uint64 sessionId` |
| Error | 24 | `0xFF` | `0xFF` | `int32 HRESULT` |

Golden OK (session 1): `444f544e45545f4950435f5631001c00ff0000000100000000000000`.
Golden error (`0x80131515`): `444f544e45545f4950435f5631001800ffff000015151380`.

`decodeReply` reads exactly 20 bytes, checks magic and `reserved == 0`, checks `size` is 24 or 28, then reads exactly `size - 20` bytes into a stack array of 8. It never allocates from the length field. HRESULT mapping: `0x80131515` (NOTSUPPORTED) and `0x80131385` (UNKNOWN_COMMAND) -> `unsupported`; `0x8013135b` (NOT_YET_AVAILABLE) and `0x80131371` (RUNTIME_UNINITIALIZED) -> `busy`; everything else -> `rejected`. The number is kept in `Error.Code`.

Nettrace preamble the probe checks (first 102 bytes of the stream; layout from the NetTrace v4/v5 doc fetched today and the existing test string):

| Offset | Bytes | Meaning |
|---|---|---|
| 0 | `Nettrace` | magic (8) |
| 8 | `14 00 00 00` | int32 20 |
| 12 | `!FastSerialization.1` | 20 chars |
| 32 | `05 05 01` | begin object, begin type object, null ref |
| 35 | int32 | object version (expect 4 or 5) |
| 39 | int32 | minimum reader version |
| 43 | `05 00 00 00` + `Trace` | type name |
| 52 | `06` | end of type object |
| 53 | 8 x int16 | sync time (year..ms) |
| 69 | int64, int64 | QPC sync, QPC frequency (must be > 0) |
| 85 | int32 | pointer size (4 or 8) |
| 89 | int32 | process id (> 0) |
| 93 | int32, int32 | processors, sampling rate |
| 101 | `06` | end of Trace object |

`ParsePreamble` is a fixed-offset reader over at most 102 bytes. Fewer bytes -> `bad-stream`. Wrong literal, wrong tag, name length not 5, version outside 4..5, pointer size not 4 or 8 -> `bad-stream` with the offending number in `Code`. Block parsing is step 2.

### 3.4 Transports

Windows (`dial_windows.go`). All handles are non-inheritable. Order inside `Dial`:
1. `pipe = \\.\pipe\dotnet-diagnostic-` + `strconv.FormatUint(pid)`. The name is built from the number only; no string from any caller.
2. `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)`. `ERROR_INVALID_PARAMETER` -> `not-running`. `ERROR_ACCESS_DENIED` -> `diag-denied`. `GetExitCodeProcess != STILL_ACTIVE` -> `not-running`. `GetProcessTimes` -> creation ticks. If `t.StartTicks != 0 && != ticks` -> `peer-mismatch`.
3. `CreateFile(pipe, GENERIC_READ|GENERIC_WRITE, 0, nil, OPEN_EXISTING, FILE_FLAG_OVERLAPPED|SECURITY_SQOS_PRESENT|SECURITY_IDENTIFICATION, 0)`. SQOS identification means the server can learn who we are but cannot impersonate us. Same flags as the keeper client.
   - `ERROR_FILE_NOT_FOUND`/`ERROR_PATH_NOT_FOUND`: process is alive (step 2) -> `diag-disabled`.
   - `ERROR_ACCESS_DENIED` -> `diag-denied`.
   - `ERROR_PIPE_BUSY`: `WaitNamedPipe(pipe, 250 ms)` in a loop until the dial deadline (default 5 s) -> `busy`.
   - anything else -> `other`, `Code` = the Win32 error number.
4. `GetNamedPipeServerProcessId(h)`. If it fails or `!= pid`: `CloseHandle`, return `peer-mismatch`. THIS IS THE PEER CHECK. No write has happened.
5. Read the creation time of the server process (it is `pid`, step 2 already did; the second connection re-reads and compares to the first). Close the process handle.
6. Return an overlapped conn: one event per direction; every read and write waits at most until the deadline, then `CancelIoEx` and `GetOverlappedResult(wait=true)` (same as `keeper/pipe_windows.go:263-298`). `ERROR_BROKEN_PIPE`/`ERROR_PIPE_NOT_CONNECTED` on read = end of stream.

Test seam: the dialer struct has `nameFor func(pid uint32) string` (default standard name) and `allowSelf bool`, set only by tests, so CI can talk to an in-process server over a real named pipe.

The pipe is created by the runtime with default security. Per the groom (inferred, not proven) that gives SYSTEM, Administrators and the creator full control and everyone else read only. We need write, so a plain user of another account is denied and SYSTEM is allowed. Named pipes are not per-session, so session 0 versus interactive does not change the name or the ACL. What is unproven: the real DACL on a real IIS worker (check (c)).

Linux (`dial_linux.go`, local proof only). Directory: `$TMPDIR` or `/tmp`. Name: `dotnet-diagnostic-<pid>-<key>-socket` where `<key>` is field 22 of `/proc/<pid>/stat` (start time in jiffies), built exactly (no globbing). `Lstat`: must be a socket and owned by the process's uid. `net.DialUnix`, then `SO_PEERCRED` (`golang.org/x/sys/unix`, module already required): `ucred.Pid == pid`, else `peer-mismatch`. `StartTicks` here is the jiffies value (opaque, equality only). The runtime's pid in a container can differ from ours; the `SO_PEERCRED` pid is then ours. That is a known limit; Linux is a proof tool, not a product path.

### 3.8 Security analysis

Threat model. The probe will run as SYSTEM or admin. The only peer that can reach the parser is a process that owns a diagnostic pipe we chose by PID. The realistic hostile peer is a compromised or malicious app inside the target process (for example one app in a shared pool), which can write any bytes on its own diagnostic port. Second: a low-privilege process that creates a pipe with the same name first (name squatting).

Rules, each with a test:
1. Fixed commands. Two encoders exist, `encodeStart()` with no arguments and `encodeStop(id uint64)`. No API takes a provider, keyword, level, command id or PID-derived string. A test lists the exported surface and fails on any new exported name.
2. Peer check before the first write. The server PID of the connection must equal the PID the owner named. The creation time must equal the first dial's (second connection) or `--start-ticks`. A mismatch closes the handle with nothing sent. Squatting fails here.
3. No impersonation. SQOS identification. The probe asks `GENERIC_READ|GENERIC_WRITE` and nothing else; it opens the process with `PROCESS_QUERY_LIMITED_INFORMATION` only. No debug privilege, no `PROCESS_VM_*`.
4. Every read and write is bounded in time (deadlines + `CancelIoEx`) and size: reply max 28 bytes into a fixed array; preamble max 102 bytes; stream chunks of 4 KiB into one reused buffer; 128 bytes kept; 4 MiB read cap. Nothing allocates from a number the peer sent.
5. Fail closed. Unknown magic, size, command, tag or version stops the probe. No "skip unknown" in step 1.
6. No trace data leaves the process. Nothing is written to disk. Nothing from the stream is printed or logged, not even a hex dump. The text and JSON hold only the numeric and boolean fields of `Result`. (Reason: Microsoft calls the port sensitive, and the .NET 10.0.15 stop path emits the process command line even with rundown off, per the groom.)
7. Go is memory safe, so a parser mistake is a panic, a stall or a wrong number, not code execution. The panic is recovered and the stop path still runs. The stall is bounded by deadlines. A wrong number cannot reach any chart in step 1 (the probe records nothing).
8. The probe changes nothing in the target except the session it starts and then stops. It sets no environment variable, loads no profiler, takes no dump.

Residual risks, plainly: (a) `GetNamedPipeServerProcessId` names the process that created the pipe; a process holding a duplicate of the server handle is not detected. The target would have had to hand it over. (b) The session is real work in the target for 20 s: the unmeasured overhead. (c) A diagnostic port in "connect mode" (`DOTNET_DiagnosticPorts`) may have no default pipe: shows as `diag-disabled`.

### 3.9 Footprint

- Probe process: about 10 MB working set (Go runtime), a 4 KiB read buffer, under 100 ms CPU total, almost all of the 20 s blocked on I/O. One goroutine plus the Go runtime's own. No network, no disk.
- Service: untouched in step 1. The executable grows by the codec (about 60-100 KB estimated; measure in the PR).
- Target: one EventPipe session, 1 MiB buffer, `System.Runtime` counters every 5 s, no stack walk, no rundown. Unmeasured. S4 measures.
- Windows CI: the added tests are in-process and finish in under 5 s (durations are set to 50-300 ms in tests).

## 6. BL-113: VMware balloon, `vm` group (full)

### 6.1 Scope
In: group `vm`, field `vm.balloonBytes`, the "not applicable" outcome, the capture command `vm-probe`. Out: `vm.stealPct` (blocked, section 6.10), Hyper-V, Azure, EC2, GCP (the research found no guest-visible steal or balloon counter), SMBIOS/CPUID labels, `Maximum Memory, Mbytes`. The owner decides the BACKLOG wording "VMware only".

### 6.2 Behaviour
- Reads one PDH counter, English path `\VM Memory\Memory Ballooned in MB`. Source: a 2020 VMware document [OLD]. NOT verified on a real guest. The capture command (6.8) exists to verify it.
- Unit: MB as VMware states it. Treated as MiB (x 1,048,576), the ESXi convention. This is an assumption; `vm-probe` output plus a known balloon size on a lab VM settles it.
- Gauge. A value of 0 is a real reading ("nothing taken back") and is written as `"balloonBytes":0`. A missing, failed, negative, NaN, infinite or implausible (> 16 TiB) reading writes nothing and the group is named in `Missing`. Never a zero for missing.
- `stealPct` is never written by this group. It stays absent.
- Optional group (budget probation applies).
- Where the counter object does not exist (physical servers, Hyper-V, clouds, VMware without Tools perf library): outcome "not applicable": the group is silently absent. No `Missing`, no chart note, no diag line. It looks again every 30 minutes (Tools may be installed later).

Outcomes:

| Host | Result |
|---|---|
| VMware guest, Tools perf counters present | `"vm":{"balloonBytes":N}` each tick |
| Physical, Hyper-V, cloud, no VMware Tools | nothing written, nothing in `Missing`, re-probe every 30 min |
| VMware guest, counter exists but read fails or is invalid | tick has no `vm`, `Missing` has `vm` |
| Probe or add fails for another PDH reason (not a known "absent" status) | `unavailable` as today: `Missing` has `vm`, retry on the existing 15 s doubling backoff up to 5 min |
| Group too slow twice | `vm: slow`, 10 min probation (existing rule) |
