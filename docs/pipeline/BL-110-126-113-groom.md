## 2. What the research found that matters

BL-110 / BL-126:
- [INFERRED] Default Windows pipe `\\.\pipe\dotnet-diagnostic-{pid}` is created with NULL security attributes, so LocalSystem gets full control. SYSTEM to w3wp should work with no restart. Never tested; proof is owed. (Name with `-socket` suffix is Unix only.)
- [SOURCE] Wire format: 20-byte header (`DOTNET_IPC_V1`, u16 length, command set, command id), EventPipe set 0x02. `CollectTracing3` = id 0x04 (spec text says 0x0203 in one place, wrong). Stream after the reply is NetTrace; stop with `StopTracing` (0x01) on a second connection.
- [SOURCE] .NET 10 adds `CollectTracing5` (id 0x06): event-ID allow/deny filter. That is what makes BL-126 narrow (event IDs 4 and 10 only).
- [SOURCE] NetTrace: .NET 10.0.15 writes format 1 / object version 4. V4/V5 spec is enough; V6 is not needed.
- [INFERRED] Use the two EventCounter providers `System.Runtime` and `Microsoft.AspNetCore.Hosting`, 15 s interval, fixed allowlist of counters, no stacks, no rundown, ~1 MiB buffer.
- [SOURCE] No overhead numbers exist for this setup ("no data found"). Only a 2019 maintainer anecdote. We must measure ourselves.
- [SOURCE] Microsoft calls the diagnostic port sensitive (dumps, command line, profiler attach). [SOURCE] .NET 10.0.15 stop path emits the process command line even with rundown off: raw traces must never be stored; decode and drop.
- [INFERRED] Safe client rules: open with SQOS identification (no impersonation), check `GetNamedPipeServerProcessId` equals the target PID and creation time before writing a byte, repeat on the stop connection. Fall back to `proc10` when blocked.
- [SOURCE] Go options: no mature client. `Rethunk-Tech/go-nettrace` v0.2.0 (MIT) is a reference only (CPU stacks focus). Write our own narrow codec.
- [INFERRED] .NET Framework 4.7.2 is out of scope here: it stays on `clr` (BL-109, PDH).

BL-113:
- [INFERRED] VMware Tools gives `\VM Memory\Memory Ballooned in MB` (gauge, MB). Safe to add after a live check. Source is a 2020 VMware doc [OLD]; no per-version matrix found.
- [SOURCE] `\VM Processor(*)\CPU stolen time` is cumulative ms in AppDynamics' raw field, but PDH formatted values can be off by 10,000x and multi-vCPU sums pass 100%. [INFERRED] do not ship a percent until a raw capture is compared with ESXi `cpu.ready`.
- [INFERRED] Hyper-V guests: only `Maximum Memory, Mbytes` (a config ceiling). Steal and dispatch counters belong to the host. Azure, EC2, GCP: credits and scheduler wait are platform metrics, not PDH. Skip all.
- [INFERRED] Detect by probing the PDH objects, not by CPUID. SMBIOS and CPUID are label hints only and not needed for the counters.

## 5. Risks and unknowns

Security
- Attach is a real side effect in the target: a diagnostics session buffers events inside the target process. Microsoft says the port can expose secrets and run commands. Our client must be fixed-command only: no arbitrary PID, provider, keyword or command id from any API. SYSTEM talking to a pipe owned by a lower-privilege process: a fake pipe could try to trick the service. Mitigation: SQOS identification, server PID plus creation time check before the first write, bound every read length.
- The stream parser reads untrusted bytes in a SYSTEM service. Hard caps on block size, depth, strings, queue. Fail closed on unknown versions. Fuzz test the parser.
- Raw trace data holds command line and (for BL-126) type names and addresses. Never write a trace file, never log payloads. Only allowlisted numbers reach the JSON-lines.
- BL-126 type names can reveal customer code names. The recordings folder is today readable by every local user (BACKLOG BL-123 text). Needs the same admin-only folder lock as `<folder>\sql` before any type name is stored. Keep names out of default MCP and Lite exports.
- Hardened sites set `DOTNET_EnableDiagnostics=0` / `_IPC=0`. Honour it: report `diag-disabled`, keep `proc10`. Never change a target's environment.

Windows-only / platform
- Everything real is Windows. On Linux the PDH stub always errors, so group tests use fake sources.
- Pipe access across sessions (Session 0 to Session 0 and to interactive), x86 pools, filtered admin tokens: not proven.
- IIS in-process (w3wp itself) vs out-of-process (child dotnet.exe): `resolve.go` already handles the child; EventPipe must attach to the process that loaded coreclr.
- Counter semantics: `Critical` threshold with keyword 0 may or may not deliver counters; research itself says verify. If Critical drops the counters, the Hosting `RequestStart` event (method + path) would leak path text: need a denylist (`CollectTracing5`) or a different level. Must be tested on a real runtime.

Footprint
- Blackbox budget: 1% of one core mean, 1 s per group, 128 MB private (`budget.go`). A reader goroutine per target plus parser state must stay inside it. Cap targets (config already caps 32; EventPipe sessions need a smaller cap, e.g. 4, SPEC to set).
- Target-side cost unknown (no published data). Default OFF until S4 numbers exist.
- Session leak: if the service dies, the target keeps a session until the next failed write. Research says detection can be delayed when idle. Must test kill -9 of the service.

Rollback
- All steps are additive. Config switch off = no session opened. Stop path closes the owned session. `proc10` is untouched.

BL-113
- Counter identity unproven: path exists in a 2020 VMware doc only [OLD]; no per-Tools-version list. Wrong scale on CPU stolen would show false steal (research: 10,000x).
- A group that is "unavailable" everywhere except VMware must not clutter `Missing` (needs the not-applicable outcome).
- Ballooned MB is not the same as guest pressure; label it plainly ("memory the host took back"), no severity threshold.

## 6. Acceptance per slice (testable)

- S1: Codec round-trips every message against byte fixtures from a real runtime. Header with wrong magic, length mismatch, oversize length, short read are all rejected with a fixed error and no allocation beyond the cap. The client refuses to write if the server PID does not equal the expected PID. `diag-probe` prints the fields in section 4 and exits non-zero with a fixed code on denied, absent, busy. It sends no command other than start and stop.
- S2: Reader decodes a real .NET 10.0 stream to the EventCounters events with exact values; truncated or corrupt stream returns a typed error, never panics; fuzz run of N seconds finds no panic; memory stays under the cap on a 100 MB crafted stream; unknown block kinds are skipped only where the format allows.
- S3: Per selected .NET 10 target, one record per sample with only allowlisted fields; a target that is not running, denied, disabled or busy is missing with a reason and never 0; the sample JSON contains no provider string, path, command line or exception text (golden test); two baselines before any rate; recycle of the target (new creation time) closes the old session and opens a new one; with the switch off no pipe is opened (test with a recording fake transport); `proc10` output is unchanged.
- S4: A written table of target deltas for the three modes, with run-to-run variance; service kill test shows the target session ends within a stated time.
- S5: Request cannot name a PID, provider or keyword; deadline holds when the UI closes; second request while one runs is refused; cancel ends the session.
- S6: Decodes GCAllocationTick_V4 / GCHeapStats_V2 from a real stream; unfiltered events are not requested (filter IDs 4 and 10 verified in the start request); output holds only aggregated counts and approved names.
- S7: Dialog shows measured cost or "unknown"; stored result is only in the locked folder; result card says "allocated, not retained".
- V1: With a fake source returning 512 MB ballooned the group writes `vm.balloonBytes = 536870912`; invalid status or missing object writes nothing (never 0); on a host without the object the group is absent and `Missing` has no "vm" entry; chart shows the line with the existing label.
- V0: Capture output lists the VM objects and counter names present, no other counters.
- V2 (later): stolen percent equals ESXi `cpu.ready` converted, within an agreed tolerance, on a real VM under contention.
