## 1. New finding F1: can the normal run see the machine journal at all? (UNVERIFIED, needs 5 minutes on the PC)

The machine journal folder gets `AdminOnlySDDL` = `O:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)` (`sddl.go:54`). A normal (not elevated) `--recover` run does, in this order:

1. `r.JournalPending(true)` (`cmd/unravis-setup/recover.go:49`). It calls `os.Stat` on the journal file.
2. `r.MachineJournalTrusted()` (`recover.go:50`). It calls `datadir.ReadFolderSecurity`, which opens the folder for `READ_CONTROL`.

A standard account (or an administrator's filtered token) holds no entry on that folder. [INFERRED, not run] Windows then answers access denied to both. If so:
- step 1 returns false, so the run prints "Nothing to put back" and never asks Windows for approval;
- the app's own check (`internal/update/journalpending.go:39-44`, an `os.Stat` too) never sees a machine journal either.

That would make the machine half of BL-170 dead on a real PC, and S4 (the notice before the approval prompt) would never be reached. The fake in the tests answers "yes" to every read, so no test could see it.

Probe (P0, no code): elevated PowerShell makes a folder `C:\ProgramData\Unravis Probe`, runs `icacls` with `/inheritance:r /grant:r "SYSTEM:(OI)(CI)F" "Administrators:(OI)(CI)F"`, writes a file `j.json` in it. ### S2 (BL-183 a, finish): prove the machine journal, then read it through the proven handle

Behaviour. For the elevated scope, no byte of the journal is read until all of this holds:
1. Every folder from `Dirs.ProgramData` down to the journal folder is a real folder (no symlink, no junction). `ProgramData` itself is checked only for being a link: its stock list lets Users create folders, so the admin-only rule applies to the journal folder only.
2. The journal folder passes the existing `datadirCheck` (owner SYSTEM or Administrators; nobody else can write or change it).
3. The leaf is opened once, without following a link, share-read only, and on that handle: it is a disk file, not a directory, not a reparse point, link count 1, the final path equals the expected path, its owner is SYSTEM or Administrators (see "Owner rule"; the account running is not trusted), and nobody else can write it (existing `checkAdminOnly` list rule).
4. At most 8 MiB is read from the same handle. A larger file is refused. (8 MiB equals the app's own limit in `internal/update/journalpending.go:80`, so the two never disagree.)
5. Only then is it parsed.

A failed proof returns `found = true` and an error. It never looks like "no journal". The file is never deleted or changed on a refusal. `JournalPending(true)` returns true for a refused journal (the replay reports it), false when the file is absent or the journal is marked committed. Both go through one function, so there is one read path.

The unelevated (per-user) scope is unchanged: path read of the person's own file, as the person.

Owner rule (pure, `journalFileOwnerOK(owner string) bool`; amended 2026-11-22 after review of PR #83): true only when owner is `S-1-5-18` (SYSTEM) or `S-1-5-32-544` (Administrators). The account that runs the elevated copy is NOT trusted as owner (this replaces the first version, which also accepted `self`, the elevated process's own token user). Reason: a normal administrator runs an elevated and an unelevated process under the same account, and the owner of a file always holds WRITE_DAC, which no entry in the list shows. An unelevated program of that person could open the file, grant itself write, change the undo list and put the list back, and the file would still look administrators-only. A group the unelevated token holds only as "deny only" (Administrators) has no such right. Cost: a journal owned by the person's own account is refused and kept. So the writer must not leave the owner to the token's default (UAC off, the built-in Administrator account and the policy "Default owner for objects created by members of the Administrators group = Object creator" all give the user SID): `Journal.save` for the elevated scope creates the temp file with `MachineJournalFileSDDL` (`O:BAD:P(A;;FA;;;SY)(A;;FA;;;BA)`) through `FileSecurity.CreateFileSDDL`, then renames it (a rename keeps the file's own descriptor). An elevated token holds Administrators with the owner flag, so no privilege is needed. Test: a Windows test writes a journal with the real writer and reads it back with `ReadFileProven`, forcing no owner (`TestTheRealJournalWriterMakesAFileTheRealReaderAccepts`). [NOT VERIFIED] what owner a journal made by an older build has: such a file may be refused; the PC run (P2) logs it.

Contract of the reader (also amended): `ReadFileProven` returns `os.ErrNotExist` only for a file that is not there; any other error, `ErrNotProven` or not (a sharing violation, access denied), means "a journal was found and refused": `found = true`, the file is kept, never replayed, never counted as absent. Callers must not test only `errors.Is(err, ErrNotProven)`. The folders above the file are proven by the caller before the open (a junction in the middle that points at a folder without the file would otherwise look like an absent file).

## 4. Security analysis

- S2 attack: a standard user plants `C:\ProgramData\Unravis Setup\journal.json` (or makes the folder a junction to a folder of theirs) so the next elevated run replays undos they chose (delete any file, set any service). Today (master after #70): folder link and folder list are checked; the file is still read by path (`os.ReadFile`, follows a leaf link, no size limit), and `JournalPending` parses before any check and `NewJournal` re-reads by path. After S2: no byte is read before the folder and the leaf are proven on one handle; link, hard link, owner and write list of the leaf are checked; size is bounded; there is one read path.
- Residual S2: an administrator-level attacker can still write a journal; that is outside the model. A swap between the folder check and the leaf open needs delete or rename rights on an admin-only folder, or on `ProgramData` (Users have create only there). Step 4 (final path) catches a folder swapped for a link. Not covered: an oplock race by a process that already is an administrator.
- S1 attack: replace `blackbox.json` between proof and read to feed the SQL service another config (another target folder, another port). After S1 the proof and the read are the same handle, and while it is open no writer, rename or delete is allowed (share-read only). A hard link is refused (link count), so a file linked from a user-writable place cannot pass. Residual: the folder lists above the file are proven at install-sql and enable-sql only (decision 5, kept).
- S1 privilege: the open asks `GENERIC_READ`; the service holds `FILE_GENERIC_READ` on the file (`maskSQLSettings`, compile-time checked against `windows.FILE_GENERIC_READ` at `sqlservice_windows.go:25-29`), which includes `READ_CONTROL`. No new grant. No new right on any folder.

## 7. Footprint

- CPU: each check runs once per service start (S1), once per `--recover` (S2, S4), once per setup preflight (S3). Nothing in the 15 s sampling loop. Microseconds to a few milliseconds.
- Memory: S1 at most 1 MiB + parse. S2 at most 8 MiB read, about 3x during JSON parse, freed after the run. S4 one goroutine blocked in `MessageBox` for at most 10 minutes.
- Network: none.
- Disk: none new. No new file, no format change.
- S1 retry: at most 300 ms of sleep, only on a sharing violation.
- Binary size: a few KB.
