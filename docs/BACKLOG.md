# Unravis backlog and checklist

One shared list for every chat and session. Open it before starting work and tick items when they are done and verified.

## How to use this file

- **Add an item:** append one line under the right section. Format: `- [ ] **BL-NNN** Title. One line of why or what. (source: chat/date)`. Take the next free number.
- **Tick an item:** change `[ ]` to `[x]` only when it works on the real data path (project rule in `CLAUDE.md`) and add `(done YYYY-MM-DD, rcNN)` at the end. Say plainly if it is verified on live data or not: `live-verified` or `demo-only-verified`.
- **Never delete an item.** If it is dropped, change it to `[~]` and write why.
- **Deferred** means the owner said "not now", with the reason. Do not build a deferred item without the owner's go.
- Keep each line short. Detail goes in the plan under `.forge/<work-item>/`.

Legend: `[ ]` open, `[x]` done, `[~]` dropped.

## Daily security and performance sweep 2026-11-21 (read-only code review; nothing built, nothing ticked)

Scope: the whole tree (history starts inside the 7-day window), weighted to the update chain, setup, the Blackbox service and the app's timers. Each item was checked by reading the code; none was run (Windows-only paths are not run on Linux). Ids use `SWP-` so parallel branches do not collide on `BL-` numbers; renumber when merging. Ranked most severe first.

- [ ] **SWP-1021-1** [Medium, security] Setup locks the Blackbox folders by path, not by handle, and never checks who owns them or whether they are links. `blackbox.Manager.Install` relies on `OSEnv.SecureDir` (opens the folder without following a link, refuses a folder owned by another account, sets owner and ACL through that handle; `internal/blackbox/service_secure_windows.go:84-143`) and on `SecureCreator`/`FolderGuard`. The setup program's `bbEnv` (`internal/setup/plan.go:570-585`) implements neither: its `SecureDir` calls `Txn.SetSDDL` -> `osSecurity.SetSDDL` -> `SetNamedSecurityInfo(path, owner=BA, protected DACL)` (`internal/setup/os_windows.go:532-542`), which follows a junction. The preflight for the recordings folder only does `os.Stat` (`internal/setup/preflight.go:337-352`). The default recordings folder is a predictable drive-root name, `D:\UnravisBlackbox` (`internal/blackbox/config.go:28`), where ordinary users can usually create folders. `PublishThisPC` also does `os.MkdirAll(%ProgramData%\Unravis Blackbox, 0o755)` and only then locks it (`internal/blackbox/publicconfig.go:44-47`), so the same applies there. Failure scenario: a standard local user creates `D:\UnravisBlackbox` as a junction to a folder they cannot read (another account's profile, an app folder); an administrator later installs the Blackbox through Unravis setup; the elevated worker sets Administrators as owner and a protected ACL with Users read/execute on the junction target and inherits it down the tree, so the target's files become readable by every local user (or its ACL is broken), and the recorder writes into it. Proposed fix: make `bbEnv.SecureDir` journal the old SDDL and then call the handle-based `blackbox.OSEnv{}.SecureDir` (no-follow, owner check); implement `SecureCreator` (create with the ACL in the create call) and `FolderGuard` on `bbEnv`; in `checkRecordingsFolder` use `Lstat`, refuse a link and a folder owned by a non-administrator; in `PublishThisPC` create the folder with the ACL in the create call (as `MkdirSDDL` does) instead of `MkdirAll` then lock. Add a Windows test with a junction as the recordings folder. Needs a Windows run to tick.
- [ ] **SWP-1021-2** [Low-Medium, performance] The silent updater re-hashes the whole setup program every minute while a failure stays on screen. `autoStep` (`internal/server/updater_auto.go:167`) evaluates `u.fileStillThere(m)` (reads and SHA-256s the downloaded setup file, tens of MB) before it checks `u.autoFailed()`. When the person's own "Apply now" failed (state stays `failed`, `autoFailed()` false), every 1-minute tick reads the file and then returns. It stops only when the state changes. Fix: test `u.autoFailed()` first (a bool), and call `fileStillThere` only when it is true; or remember the check result per `(version, state)`.
- [ ] **SWP-1021-3** [Low, performance] The always-on recorder reads the whole new program into memory to hash it. `fileSHA256Hex` uses `os.ReadFile` (`internal/blackbox/selfupdate.go:501-507`), and the staged program may be up to `maxProgramSize` = 200 MiB (`selfupdate.go:42`), against the Blackbox budget of 50 MB working set (BL-122). One-off per update, but it lands in the service that must stay small. Fix: hash from the open file with `io.Copy` into `sha256.New()` (`stageFromZip` already streams the copy). Same pattern, not always-on, lower priority: `LaunchRollback` reads the whole old setup to look for a text marker (`internal/update/launch_windows.go:60`; `update.SetupCanRecover` already does this in 1 MB pieces) and `setupCanBeRolledBackTo` reads it whole during an upgrade (`internal/setup/plan.go:941-951`).
- [ ] **SWP-1021-4** [Low, network] A feed that fails a trust check is retried at full rate forever. A rejected result (expired manifest, bad signature) carries no `Backoff` (`internal/update/fetch.go:330`), so the app and every standalone recorder check again at the normal 30-minute cadence, each time fetching both files and making one retry after 3 s (4 requests per check, no ETag because the cache is filled only after a good verify). The expired-feed case is the known "frozen fleet" risk (OTA research). Fix: set `Backoff: true` on a rejected result after the retry (the existing doubling, capped at 6 h), so a broken or expired feed costs the fleet little; the first good feed then resumes within the cap, and Check for updates in the app still runs at once.
- [ ] **SWP-1021-5** [Low, design to confirm with the owner] The signed control file (pause, withdraw, staged rollout) fails open on the internet path. `fetchControl` returns nil on any fetch or verify problem and `applyControl` holds a release only when a live, remembered control file says so (`internal/update/fetch.go:393-410`, `433-446`; only the folder path sets `required`). A machine that has never seen a control file, or whose remembered one expired (up to 90 days), installs a withdrawn or paused release when the control file cannot be fetched (a blocked or rate-limited host, a network that drops one URL). It cannot install anything unsigned; the effect is that a withdrawal does not reach every machine. Options: accept and document; or hold for a short grace window (for example 24 h after the manifest's `published` time) when no live control file has ever been read for the channel, then fail open. Owner decision.
- [ ] **SWP-1021-6** [Low, performance] `Updater.Status()` reads the update-result file from disk on every call while it holds `u.mu` (`internal/server/updater.go:205-209`, and again in `resultIsFromThisLaunch`, line 376). Every screen poll pays a disk read and blocks the check loop and the minute tick (`availableManifest` takes the same lock) if that disk is slow. Fix: read the file outside the lock, or cache it by file modification time.

Checked and found sound (no item): signed manifest and control parsing (strict, signature before parsing, channel and key role, rollback and same-seq pins), download hash and size on write and again from disk, hand-off to the installer (file held open while hashed and started; setup holds its own file open and the elevated worker repeats the check), the Blackbox self-update path (package name, program hash from the signed manifest, `StartVerified`), the elevated journal replay (BL-183 a: link and owner checked before parse), the recorder's HTTP server (key before throttle, bounded failure table, connection caps, no-follow file open), and the workflows (actions pinned by commit, inputs passed through `env`).
