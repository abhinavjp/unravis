8/11 Your decisions

All 12 decided (Oct 30). Your picks are ticked. Two differ from what we suggested: D-2 and D-4 (marked below). You can still change a tick here; it only affects this page.

0 of 12 decided

D-1 Separate rows or one row

When the trace chart shows the API log, the SQL log and the web-server log on the same clock, should each one get its own row, or should they all share one row?

ELI10 It is like a school sports day results board. If all the runners are printed on one line you cannot tell who is who; if each class gets its own line you can see each class at a glance.

Why it matters: If the three logs are mixed on one row, a slow login at 14:03 is hard to read because you cannot tell whether the dot is an API call, a database event or a web request. If they get separate rows, the chart is taller and shows more, but the picture is clearer.

Why we suggest B: Separate rows are the decisive choice because a slow login has three parts and you need to see which part moved first; the price is a taller chart that uses more screen space.

D-2 Keep both ways in changed from our suggestion

The app already has a guided investigation with eleven numbered steps. Should the new trace view replace it, be the only way in, or should the case home offer both?

Your ruling: You chose A, we had suggested C (offer both). Tracing replaces guided as the front door: the case-home Guided button is swapped for a Tracing button. The guided screens, charts and code stay in the app, just not offered on the case home, so they can be reused later. Nothing is deleted.

ELI10 It is like a school with two doors. You can close the old door and use only the new one, or keep both doors open so people can pick the way they know.

Why it matters: The eleven-step guided investigation already works and some people rely on its checklist. If tracing quietly removes that door, those people lose a working method. If both are offered, the case home has two starting points, which needs clear labels so nobody gets lost.

Why we suggest C: Keeping both is decisive because guided already works today and its checklist is used, so removing it would break those people; the price is two entry points that must be labelled clearly.

D-3 What the web row shows

On the web-server row, should each time slice show only how many requests happened, or also how long they took, or also whether they failed?

ELI10 It is like a post office report. You can count how many parcels came in, or also say how long each took to sort, or also say how many were refused at the counter.

Why it matters: If the web row only counts requests, a spike in slow or failed requests can hide behind a normal-looking count. Adding time and failure type makes the row more useful but adds details that are not always present, so the picture can look more certain than it is.

Why we suggest C: Showing counts, time and failure type together is decisive because a customer error at 14:03 needs both how long and whether it failed; the price is that the time is approximate and status is missing in some logs.

D-4 How far a trace reaches changed from our suggestion

What is the longest stretch of time one trace can cover, and how big a stretch does it open with?

Your ruling: You chose A but with a longer window: up to one month (30 days), opening at the last hour. We had said 7 days. The audit lane aggregates on the server so the chart stays at 120 buckets or fewer (6-hour buckets at 30 days).

ELI10 It is like choosing the paper for a drawing. A long roll of paper shows a whole week but each day is tiny; a short sheet shows one hour in fine detail but cuts the week off.

Why it matters: A very long window covers a week-long incident in one picture, but the chart buckets become coarse and the read is slower. A short limit keeps the picture sharp and fast but cannot show an incident that ran for days.

Why we suggest A: A seven-day cap is decisive because it matches the limit the guided steps already use, so one rule covers both; the price is that very long windows show coarse hour-sized buckets.

D-5 Where the API row gets data

When the chart shows the API audit row, should it only show data from a live database you have connected, or should it also have built-in sample rows so the chart always shows something?

ELI10 It is like a weather map that only lights up when you plug in your own sensor, versus one that also has a pretend town so you can see how it looks before you plug anything in.

Why it matters: If the API row has nothing to show every time no database is connected, you and your colleagues cannot tell the chart is working. If sample rows are mixed in carelessly, someone could read fake data as real.

Why we suggest B: The chart always has something to show for training and for automatic tests, while real data still appears once a database is connected. The main thing you give up is extra work to create and clearly label the sample rows.

D-6 How the chart asks for data

Should the new tracing chart use a brand-new web address of its own, or should it add a switch to the address the existing text timeline already uses?

ELI10 It is like adding a new door to a building for a new room, versus putting a hidden switch on the old door that changes what the room looks like inside.

Why it matters: If the chart and the existing text timeline share one address, a change meant for the chart can accidentally change or break the text timeline that already works.

Why we suggest A: The existing text timeline keeps working exactly as it does today, and the new chart can ask for data in its own shape without risking the old screen. The thing you give up is a little code reuse and a second address to look after.

D-7 Which SQL data shows first

For the SQL row in the first version, should the chart show SQL data you already saved into the case file, or read it fresh from the SQL Server when you press the button, or both?

ELI10 It is like a photo album that only shows pictures you already printed and filed, versus a live camera feed, versus having both the album and the camera side by side.

Why it matters: If the SQL row shows only fresh live data, it can vanish when you reopen the case file, and a slow or busy server can make the chart stall. If it only shows saved data, you cannot see what the server is doing right now.

Why we suggest A: Saved SQL data is already inside the case file and comes back identically on reopen, so the first version is dependable and cheap and needs no live connection. You give up seeing SQL activity that was never imported; a later release adds that live read.

D-8 Who picks the allowed cookies

When we save a scrambled fingerprint of a cookie, who decides which cookie names are on the approved list — one list for the whole app, one list inside each case file, or a different list for every import?

ELI10 It is like choosing which names go on a guest list: one list at the front door for every party, one list kept inside each party room, or a fresh list for every single guest arriving.

Why it matters: Cookies can carry login details, so a name on the list gets its value scrambled and kept. If the list is too broad or shared carelessly, more private data than intended is saved into case files; if it is per import, it is easy to be inconsistent and save the wrong thing.

Why we suggest B: Each case folder already keeps its own scrambling key, so the approved cookie-name list belongs with the case and stays private to that investigation. The thing you give up is the convenience of setting the list once for every case.

D-9 Privacy on shared files

When you send files to a colleague, should visitor addresses and cookie fingerprints be left out by default for every kind of export?

ELI10 Like mailing a school report: do you black out home addresses on every copy you hand out, or only on the short summary sheet?

Why it matters: If the wrong default is on, a colleague opens a file and sees who visited your site and from where. Fixing trust after a leak is harder than ticking the right default once.

Why we suggest A: One default protects both ways you move a case off your PC. You give up keeping visitor addresses in shareable exports unless you explicitly turn scrub off.

D-10 Saving live database reads

When you pull fresh SQL or Mongo activity into a case, should those rows live in the same event list as imported logs, or as one big saved snapshot blob?

ELI10 Like saving homework: paste each answer on its own line in a notebook, or stuff the whole worksheet photo into one envelope.

Why it matters: This choice decides whether tracing, rollups, and the 50,000-row cap treat live pulls like normal evidence. A blob can be fast to dump but awkward to chart or dedupe.

Why we suggest A: Live pulls stay part of the one case database story the tracing chart already uses. You give up the shortcut of dumping opaque JSON without event rows.

D-11 Jump to call trace

From the new tracing chart, should clicking an API audit bar optionally open the per-call trace tray for that moment?

ELI10 Like a bus map: stay on the city-wide line view, or tap one stop to see every passenger getting on there.

Why it matters: Two timelines already confuse people. A link must be optional and named clearly or users will not know which screen they are on during a customer outage.

Why we suggest B: It speeds investigation once the main chart exists without merging two UIs in MVP-1. You give up the simplest single-path navigation until that polish lands.

D-12 Split IIS by Windows code

Should the IIS lane on the tracing chart ever split into separate rows by Windows error number, labelled as an estimate?

ELI10 Like sorting gym failures: one pile for everyone, or separate bins for locked door, timeout, and wrong password—with a note that the bins are guesses.

Why it matters: Win32 codes group IIS failures differently than HTTP status alone. Splitting wrong looks like precision; never splitting hides patterns when a customer saw errors at 14:03.

Why we suggest B: It exposes IIS-specific failure patterns the HTTP code alone hides, with honest estimate labels. You give up the cleanest single-bar IIS lane.

ELI10 Pick-your-adventure cards—the spec marks which choice the authors liked, but you still choose.
