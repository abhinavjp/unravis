# Task for Muse: journey and error logging for Unravis

Repository: https://github.com/abhinavjp/unravis (branch `master`, commit 438e752). Work on a new branch `muse/logging` cut from master. Push that branch and open a pull request against master. Do NOT push to master and do NOT merge. Other work (audit-failure reasons, bare-URL access) is being applied to master at the same time by another agent, so keep your changes self-contained, rebase on master before you finish, and say which files you touched.

Go toolchain: use Go 1.2x as in `go.mod`; run `go test ./internal/... ./cmd/...` and, in `web/`, `npm run check` and the unit tests. Say plainly what you could not run. Do not use `-race`.

Repo: Unravis (Go: `cmd/audit-explorer/main.go`, `internal/server/*`, `internal/investigate`, `internal/casestore`, `internal/setup`; Svelte 5 UI `web/`, `web/src/lib/api.ts`).

## Problem (owner)
"Add enough logs to identify if there is any issue anywhere ... get to know what the user journey is and where we are facing any kind of error." Today `internal/server` has about 3 log calls; the Guided analysis failure ("audit source could not be read") could only be guessed at. The owner will send a log file to the developer.

## Required
1. **Log file.** A rotating per-user log: `%LOCALAPPDATA%\Unravis\logs\unravis.log` (use the same per-user data root the app already uses; keep it testable via an injected dir). Structured `log/slog` text lines (`time level msg key=value`), size-rotated (5 MB x 5 files, in-process, no new dependency), file created with restricted permissions like other per-user files. Also keep writing the existing console lines. Log level via env `UNRAVIS_LOG_LEVEL` (info default, debug allowed). Log the version, OS, port, data dir and the launch/resume outcome (not codes) at start.
2. **Server journey events (info).** One line per API request from a small middleware wrapped around the existing handler: `req_id` (random 8 hex, also returned as `X-Request-Id`), method, ROUTE PATTERN (never raw query strings, never ids that are secrets), status, duration ms, response size. Skip static assets and polling endpoints at info (debug only). Add named business events at the points where the user does something: source connection test, source added/edited/removed, discover run, import start/finish (counts only), case created/opened/archived/restored/freed/erased, case key unlock success/failure (no key), investigation started/finished (window length in hours, source ids, counts, `audit_failure` cause, duration), export started/finished (file kind and size), update check, settings changes, session launch/resume/forget, lock/unlock.
3. **Errors (warn/error).** Every 4xx/5xx the server returns, and every recovered panic (add a recover middleware that returns a plain 500 JSON and logs the stack), logs: `req_id`, route, status, an `error_class` slug (validation, auth, timeout, source_unreachable, source_auth, query_failed, too_many_rows, disk, locked, internal) and a sanitized message. A single `sanitize` helper must strip: connection strings and URLs with credentials (`user:pass@`), `password=`/`pwd=`/`secret=`/`token=`/`key=` values, bearer tokens, the session token, case keys, anything resembling a base64 secret over 24 chars, and file paths under the user profile (replace the profile dir with `%USERPROFILE%`). Never log request or response bodies, audit payloads, row data, or headers other than a fixed allow-list (User-Agent family only).
4. **Source and investigation diagnostics.** In the audit read (`internal/server/investigation.go` and the source query code it calls): log per source start/finish with source id, kind, window, row/call count, duration, and the sanitized failure reason, so "why could the audit source not be read" is answerable from the log. Include timeouts and the budget that was hit.
5. **UI journey and errors.** Add `POST /api/client-log` (needs the session token, body max 8 KB, rate limited 60/min, fields allow-listed: `kind` in {nav,action,error}, `screen`, `action`, `code`, `message` (sanitized and truncated to 300 chars server-side), `stage`) written at info/warn with `src=ui`. In `web/src/lib/api.ts` and the app shell: report screen navigations (screen name only, never ids or query text), key actions (button/step names: guided analysis step reached, run, retry, export), every `ApiError` shown to the user (status, code, stage, request id from `X-Request-Id`), `window.onerror` and `unhandledrejection`. Batch and send with `navigator.sendBeacon`/fetch, fail silently, never block the UI, drop when no session. Do not send field contents.
6. **Where to find it.** Add a "Support logs" section to the existing Help/About/Settings screen (find the best existing place): shows the log folder path and a "Copy folder path" button, plus one plain sentence "Send the newest unravis.log to your contact; it contains no passwords or case data." Add `GET /api/logs/info` (session token) returning path, size, newest-entry time. Mention it in the installer finish text only if trivial; skip otherwise. Update `docs/` with a short "Logs" page (what is logged, what is never logged, how to send it).
7. **Tests.** Go: sanitize table tests (connection string, bearer, `password=...`, `user:pass@host`, long base64, profile path, case key, session token - each must be absent in output); middleware logs route pattern not query; panic recovery returns 500 and logs; client-log validation (oversize, bad kind, unauthenticated, rate limit); rotation (size + count); a "no secret ever reaches the log" test that drives login/unlock/connection-test flows with known secret strings and greps the log file for them. Web unit tests (vitest if present) for batching/silent failure/no-session drop. Run `go test ./internal/... ./cmd/...` and web unit tests / `npm run check`; say what you could not run.

## Rules
Do not touch `sql/`, `.env*`, `unravis-review-pack.zip`. No new dependencies. Never log passwords, tokens, keys, connection strings, payloads or row data; when unsure, do not log the value. Keep log volume sane (no per-row logging). Match surrounding style; comments explain why. Finish by pushing branch `muse/logging` and opening a pull request against master (do not merge); put in the PR description what you changed, which files, and what tests you ran or could not run.
