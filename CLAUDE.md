# Unravis (api-audit-explorer)

- Finish what you start (owner rule, 2026-11-12): the owner tests with LIVE data, never dummy data. A feature is done only when it works on the real data path end to end. Never ship a UI that is demo-only and then ask the owner for input before doing the real part. If a real-data step needs something unknown (field names, a shape), find it yourself first through the app's own read-only code, safe sources and the repo; ask the owner only when that is truly impossible, and ship everything else in the same pass. Never end a turn with "not implemented yet" or "waiting for X" when part of the work can be built now. When a slice has a demo path and a real path, build both before reporting; say plainly what is verified on live data and what is not.
- Branches and merges (owner rule, 2026-11-22): every pull request targets `develop` (open with `--base develop`) and merges on a green `fast-build`; nothing else merges to `master` except the promotion `tools/release/Promote-Develop.ps1`. Details: `docs/ci/RELEASE-TRAIN.md`. Pull requests do not commit the generated web files (`web/dist`, `cmd/unravis-setup/ui`, `cmd/unravis-lite/ui`): the promotion rebuilds and commits them once (`docs/pipeline/dist-on-promotion.md`). No test may assert new UI text against the embedded copy (`explorer.Assets()`, `uiFiles`); read the source under `web/src`, because develop holds the last promoted files.
- Releases (owner rule, 2026-11-21): one release at a time, for every thread. Before a promotion merges to `master`, read the release lock (`GET repos/abhinavjp/unravis/contents/lock.json?ref=release-lock`; 404 or `state` `free` = go). If `state` is `held` and `holdMerges` is `true`, wait and read again. To release, run `pwsh ./tools/release/Release.ps1 -Channel rc -Yes -Requester <your thread name> -WaitMinutes 30`; never write the lock branch by hand. Details: `docs/auto-updater/RELEASE-COORDINATION.md`.
- Shared backlog and checklist: `docs/BACKLOG.md` (owner rule, 2026-11-12). Every chat adds new items there, and ticks an item only when it works on the real data path. Items under "Backlog (deferred)" are not to be built without the owner's go; today that means anything that needs a new collector or agent.
- Housekeeping (owner rule, 2026-11-26): disk space on the owner's PC is limited, so session leftovers of this repository are cleaned up automatically and permanently. `tools/maint/Housekeeping.ps1` (hooks `Stop` and `SessionEnd` in `.claude/settings.json`, plus the hourly user task `Unravis-Housekeeping` from `pwsh tools/maint/Housekeeping.ps1 -Install`) removes the scratch folders of this repository's finished sessions, `unravis-probe*` and `unravis-dev-*` in Temp, merged clean idle git worktrees under `D:\Scratch`, `Temp\claude` or `.claude\worktrees` (never forced, never deleting a branch) and caps every Go build cache at 8 GB (BL-730: not only `go env GOCACHE`, also `%LOCALAPPDATA%\go-build`, the Claude app's `Packages\Claude_*\LocalCache\Local\go-build` and `D:\GoCache\build`; the module cache is only reported). It never touches other repositories, other sessions' folders (it judges only sessions with a transcript in this repository's Claude project folder), anything a process names, uncommitted or unmerged work, the Homestretch agent's work areas, or source. Do not park large files outside the repository's worktrees and `Temp\claude\<hash>\<session>` scratchpad: put temporary output in your session scratchpad so it is cleaned with the session; do not add new places that need their own cleanup. Do not delete other sessions' folders by hand; run `pwsh tools/maint/Housekeeping.ps1 -Event manual -DryRun` to see what would go. Add a new kind of leftover to `Housekeeping.ps1`, not a new script. Tests: `pwsh tools/maint/Test-Housekeeping.ps1`. Backlog: BL-597.
